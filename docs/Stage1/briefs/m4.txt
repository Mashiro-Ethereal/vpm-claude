   - TASK.md: env id; the "Task Description", "Randomizations" and "Success Conditions" parts of the env class docstring; the list of evaluate() keys; what to produce (a candidate directory) and how to self-check it.

   - candidate_api.md (copy of vpmkit/resources/candidate_api.md), REQUIREMENTS.md (copy of vpmkit/resources/REQUIREMENTS.md), example/ (copy of vpmkit/resources/example_candidate/PushCube-v1/), never any file from candidates/reference/.
   - bundle.json: env_id, mani_skill version, files with sha256, and an overall `bundle_hash` (sha256 over sorted relative paths and contents; it must not depend on timestamps).
   Refuse env_id "PushCube-v1" (it is the example task).
2. vpmkit/resources/REQUIREMENTS.md (English, for the generating agent), covering: the candidate files; predicates only through parameters and the WorldView/ObjView API, no object names, no environment judgments; current state only; one-sentence descriptions that match the definitions exactly; English need_true/need_false templates; thresholds as keyword defaults with ranges declared in params; copying environment judgments: copy the evaluate() formula exactly into an object-parameterised predicate, declare it in the `official` block (a list of literals whose conjunction must equal one evaluate() key frame by frame), keep its thresholds out of params; the last stage's exit guard should correspond to `success` when success is a conjunction of conditions; linear stages, negation allowed, no disjunction; invariants with regress targets that can actually be re-satisfied (e.g. a lost grasp regresses to the grasp stage, not to a stage requiring an open gripper); progress with fixed scales only; no Python loops in predicates/progress; how to run the validator on the candidate (`python -m vpmkit validate ./candidate --env <env_id>` with the interpreter path given in TASK.md).
3. vpmkit/resources/generation_prompt.md: the prompt template for the generating agent (placeholders {env_id}, {bundle_dir}, {candidate_dir}, {python}, {feedback}); round 0 asks to read the bundle and write the candidate; later rounds include the previous validator/review feedback and ask for a revised candidate in place.
4. Backends (backends.py):
   - `GenerationBackend` protocol: `generate(bundle_dir: Path, candidate_dir: Path, workdir: Path, feedback: str | None, round_idx: int) -> GenerationResult(transcript_path, model, usage, returncode, duration_s)`.
   - `ScriptedBackend(source_dir, mutations: dict[int, callable] | None = None)`: copies source_dir into candidate_dir each round, then applies mutations[round_idx] (a function editing files in candidate_dir) if present. Used for tests and for exercising the pipeline without an LLM.
   - `ClaudeCodeBackend(claude_bin="claude", model, small_model, base_url, api_key_env, max_turns=60, timeout_s=3600, python=...)`: runs `claude -p <prompt> --output-format stream-json --verbose --max-turns N --model <model> --allowedTools <list> --disallowedTools WebFetch,WebSearch` with cwd = workdir. Allowed tools: Read, Write, Edit, Glob, Grep and Bash restricted to running the validator command. Environment: a copy of os.environ without any ANTHROPIC_*/CLAUDE_* variables, plus ANTHROPIC_BASE_URL=base_url, ANTHROPIC_AUTH_TOKEN=<value of os.environ[api_key_env], read at call time and never logged>, ANTHROPIC_MODEL=model, ANTHROPIC_SMALL_FAST_MODEL=small_model, and CLAUDE_CONFIG_DIR=<workdir>/.claude_config so the user's own Claude configuration and instruction files are NOT loaded. Writes the raw stream to transcript.jsonl, parses the model name from the init event and usage/cost from the final result event; a missing key, a non-zero exit or a timeout yields a GenerationResult with returncode != 0 and an error note instead of raising.
   - `ClaudeCodeReviewBackend` implementing vpmkit.validate.layer2.ReviewBackend the same way but with read-only tools (Read, Glob, Grep) and its own config dir; returns the final result text.
5. Run loop (run.py): `run_generation(env_id, backend, *, review_backend=None, out_root="outputs/stage1/runs", run_id=None, max_rounds=3, validator=validate_layer1, validator_kwargs=None) -> RunRecord`.
   - Directory: out_root/<env_id>/<run_id>/ with bundle/ (built once), work/ (agent workdir), candidate/ (current candidate), rounds/<i>/ (a frozen copy of the candidate, layer1.json, layer1.md, layer2.json when run, generation.json), run.json.
   - Round i: backend.generate -> validator(candidate, env_id, **validator_kwargs) -> if layer 1 passed and review_backend is set: run_layer2 (task text and env source from the bundle) -> passed iff layer 1 passed and (no review or review verdict "pass"). Stop at the first passing round. Feedback for the next round = layer-1 Markdown + review issues. After max_rounds failing rounds: status "failed", human_intervention = True.
   - RunRecord (JSON): run_id, env_id, bundle_hash, backend description (class, model; never secrets), per-round results (passed, layer-1 summary, review verdict, durations, usage), final status, total time, mani_skill and torch versions, git commit of the repo (git rev-parse HEAD, if available).
   - `validator` is injectable so unit tests can stub it.
