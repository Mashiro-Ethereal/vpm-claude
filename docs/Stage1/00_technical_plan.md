## 1. Stage1 做什么

对每个任务，由 agent（Claude Code 接 DeepSeek）读环境的源码，写出一个能逐步执行的过程 teacher。它通过两层检查后，作为初始候选交给 Stage2。

- **过程 teacher** 由两部分组成：一条带守卫谓词的线性阶段链（Stage Graph），以及各阶段的 progress。它读仿真特权状态，每一步给出当前阶段、阶段内进度、势值 Φ、谓词取值和 guidance。
- **Stage1 要保证三点：**
  1. 派生产物一致：阶段、Φ、guidance 出自同一结构；
  2. 能在真实环境中算出来：按 Stage2 训练时的方式（GPU、批量）运行不出错；
  3. 结构与参数分开：Stage2 的外层由 LLM 改结构，内层由 BO 调参数。
- **Stage1 不负责：**
  - 语义是否正确、进度是否好用：由 Stage2 用训练反馈检验和修正；
  - 基于 rollout 的检验，以及 Stage2 早期评价用的里程碑：都放到 Stage2（第 8.5 节）；
  - G1：推迟（第 12 节）。
- **下游对 teacher 的三项硬要求：**
  - 作为奖励时，满足 §3.3 的六条规则；
  - 能在 GPU 上对全部并行环境批量计算；
  - 能在保存的状态上离线重算，供 Stage2 分析和 Stage3 重标。
- **范围：** 先做 ManiSkill 上的 16 个单臂桌面任务（第 9 节），16 个都由 agent 生成。实现时先在 PickCube 一个任务上走通全流程，再扩展到其余 15 个（第 10.3 节）。给 agent 看的示例是一个虚构的抓放任务，不取自评测任务（第 6.4 节）。MetaWorld、LIBERO 以后再扩展。

出处：01 §1.2、§2.5、§4.5、§4.6。

## 2. 总体流程

### 2.1 一次运行怎么走

```text
环境名
 └→ 输入包生成程序 → 输入包（每个任务一份；生成后固定，记哈希）
     └→ harness 建运行目录：workspace/（输入包副本、空的 candidate/、check.sh，再 git init）与 records/（记录）
         └→ 生成 agent 读 TASK.md，写 candidate/；写的过程中可以随时运行 ./check.sh
             └→ 本轮结束 → 第一层：四项程序检查
                 ├ 不通过 → 报告交回 agent，接着原会话修复
                 └ 通过 → 第二层：审查 agent（独立会话，只读）
                     ├ 有“错误” → 报告交回 agent 修复
                     └ 没有“错误” → 通过：候选连同记录和报告交给 Stage2

首次生成算第 1 轮，之后最多修复 3 轮；第 4 轮后仍不通过，这次运行记为失败。
```

### 2.2 分工

| 谁 | 写什么 | 做几次 |
| --- | --- | --- |
| 人（基础设施） | 适配层与世界视图、通用几何工具、自动机运行时与 Teacher、两层检查、输入包生成程序、辅助函数对照表、接口说明（candidate_api.md，以及 TASK.md 中的设计规则）、示例（虚构的抓放任务）、PickCube 的参照候选（测试样例与试跑的答案）、harness、PBRS 奖励包装 | 适配层、对照表、接口说明、示例每个仿真器一份；其余与仿真器无关，只做一次 |
| agent | 每个任务的候选：对象绑定和任务特有的几何、测量函数、谓词（含阈值、模板、说明、官方对应声明）、Stage Graph、progress、notes.md | 每个任务每次运行一份 |

人不为单个任务写任何给 agent 看的内容。PickCube 的参照候选由人写，只作测试样例和试跑的答案，不给 agent 看。只有一个任务的 K 次运行全部失败时，才由人出手修改，记为一次人工介入（第 8.4 节）。

### 2.3 交付物

- 基础设施：上表“人”一行的全部内容。
- 每个任务：通过两层检查的候选，附生成记录（完整对话、每一轮的候选）和每一轮的检查报告。
- **运行与 K：** 一次运行，就是把生成流程从头跑一遍。同一任务的 K 次运行用同一份输入包，只有采样的随机性不同。首批每个任务 K = 1。

### 2.4 例：StackCube 的一次运行

候选的内容只是示意，实际由 agent 写。

1. 输入包生成程序为 StackCube-v1 生成输入包：
   - `env_source.py` 是任务类的源文件，删去两个奖励函数后由 186 行变为 145 行；
   - `helpers.py` 放入 `Actor.is_static` 的源码；
   - `scene_inventory.md` 列出 cubeA、cubeB 的尺寸与初始位姿范围、`cube_half_size` 的实际值，以及 `evaluate()` 返回的键。
2. harness 建运行目录 `outputs/stage1/runs/StackCube-v1/<运行编号>/`，在其中的 `workspace/` 里，用代码构造的环境变量和一张空闲的显卡启动 agent。prompt 只说“先读 TASK.md”。
3. agent 写出候选。下表是最后通过的版本：

   | 阶段 | 守卫 | 不变量 → 回退目标 |
   | --- | --- | --- |
   | 0 reach | `near(g, red)` | — |
   | 1 grasp | `grasped(g, red)` | `near(g, red)` → reach |
   | 2 carry | `on(red, green)` | `grasped(g, red)` → reach |
   | 3 release | `not grasped(g, red)`、`static(red)` | `on(red, green)` → reach |

   - 最后一个阶段的守卫加不变量，正好是环境的 success（红块在绿块上、静止、没被抓住），这一对应在 `official` 中声明。
   - `on`、`static` 照 `evaluate()` 的公式写，阈值照抄官方值，分别声明对应 `is_cubeA_on_cubeB`、`is_cubeA_static`。
4. 假如第 1 轮结束时，第一层报运行错误（绑定中的属性名写错），报告交回 agent；第 2 轮第一层通过，第二层查出“漏了松手”（照链走完达不到 success），交回；第 3 轮通过。这次运行记为通过，用了 3 轮，错误类别依次为“运行错误”和“能否完成”。

出处：01 §4.1、§4.3、§4.4、§4.5。

## 3. 候选的写法

### 3.1 候选目录

| 文件 | 内容 | 是否必写 |
| --- | --- | --- |
| `stage_graph.yaml` | 任务描述、对象及显示名、阶段链（守卫、不变量与回退目标）、官方对应声明、可调参数 | 必写 |
| `bindings.py` | 对象绑定：每个对象对应环境中的哪个物体、尺寸，以及挂到对象上的任务特有读数（如孔的位姿与半径）。候选中只有这个文件能读环境内部 | 必写 |
| `predicates.py` | 测量函数与谓词 | 必写 |
| `progress.py` | 个别阶段的 progress 函数 | 可选 |
| `notes.md` | 设计说明（第 6.5 节） | 必写 |

### 3.2 Stage Graph

- **线性链：** 阶段 0 到 K−1，前向边只有 k → k+1，回退箭头可以指向任一更早的阶段。不建分支图。
- **每个阶段有：**
  - 守卫（`exit`）：文字的合取，不能为空，全部成立时进入下一阶段；
  - 不变量（`invariants`，可以没有）：每条是一个文字加一个回退目标，文字不成立时回到那个更早的阶段。不变量不带事件说明。
- **没有完成节点：** 最后一个阶段的守卫后面不再有阶段，它只用于该阶段的 guidance 和 progress。最后一个阶段的守卫加它的不变量，合起来必须等于环境的 success，并在 `official` 中声明。
- **`official`：** agent 声明的对应关系，每条是“一组文字的合取 ↔ `evaluate()` 返回的一个键”。第二层审查对照源码逐条核对；程序也靠它知道哪些谓词是照官方判定改写的，这些谓词的阈值固定。
- **`params`：** 内层 BO 的搜索空间，每项写名字、默认值和范围。谓词阈值命名为 `<谓词>.<阈值名>`，如 `near.max_dist`；progress 的参数命名为 `progress.<阶段名>.<参数名>`，如 `progress.reach.d0`。默认值同时写在函数签名和 `params` 中时，两处必须相同。照官方判定改写的谓词，阈值不放进来。
- **防闪烁参数** `runtime.debounce`（即 m）保留，默认为 1。它是运行时的设置，不写进候选；参数覆盖时用这个名字（M1 的测试用它设 m = 2）。
- 字段、类型与写法的细节见接口说明 `vpmkit/resources/candidate_api.md`（第 6.3 节）。

PickCube 参照候选在 `candidates/reference/PickCube-v1/`（M3 写好，2026-10-26 你看过同意），它的 `stage_graph.yaml` 如下。`grasped`、`at_goal`、`arm_static` 照官方判定写，阈值固定，不放进 `params`；`params` 中是 `near` 的阈值和 reach 的 progress 尺度 `progress.reach.d0`（reach 照示例自写 progress，carry、settle 用默认 progress）。`near` 照示例的写法：TCP 到方块中心的距离 ≤ 方块的半对角线 + `max_dist`，只要求爪子到了方块附近（第 6.4 节）；grasp 保持 `near(g, cube)`，爪子离开方块附近就回到 reach。

```yaml
task: Pick up the red cube and move it to the goal position.
objects:
  g:    {name: the gripper}
  cube: {name: the red cube}
  goal: {name: the goal position}
stages:
  - name: reach
    exit: ["near(g, cube)"]
  - name: grasp
    exit: ["grasped(g, cube)"]
    invariants: [{literal: "near(g, cube)", regress_to: reach}]
  - name: carry
    exit: ["at_goal(cube, goal)"]
    invariants: [{literal: "grasped(g, cube)", regress_to: reach}]
  - name: settle
    exit: ["arm_static(g)"]
    invariants: [{literal: "at_goal(cube, goal)", regress_to: carry}]
official:
  - {literals: ["grasped(g, cube)"], key: is_grasped}
  - {literals: ["at_goal(cube, goal)"], key: is_obj_placed}
  - {literals: ["arm_static(g)"], key: is_robot_static}
  - {literals: ["arm_static(g)", "at_goal(cube, goal)"], key: success}
params:
  - {name: near.max_dist, default: 0.02, range: [0.0, 0.05]}
  - {name: progress.reach.d0, default: 0.3, range: [0.1, 0.6]}
```

PickCube 的 success 是“方块到达目标，且手臂静止”。最后一个阶段 settle 的守卫 `arm_static(g)` 加上不变量 `at_goal(cube, goal)`，正好等于它。

出处：01 §2.1、§4.1 第 1、6、7 条、§4.2、§4.3。

### 3.3 文字、守卫与不变量

- 文字是一个谓词实例，或它的取反，写作 `not p(...)`。
- 守卫和官方对应都是文字的合取；每条不变量是一个文字，一个阶段可以有几条。
- 不允许“或”，不允许把几个条件组合后再取反，也不允许在 YAML 中直接写数值比较。所有条件都必须是有名字的谓词。
- 真需要“或”时，写进一个谓词。官方判定也这样做：LiftPegUpright 的竖直判定对角度取绝对值，正反两个方向都算。
- `not p` 不成立时，用 p 的 need_false 模板渲染 guidance，所以用到取反的谓词必须有这个模板。
- `not p` 的真值是 p 的真值取反，margin 取 −margin(p)。margin 正好为 0 时，算 p 成立、`not p` 不成立。

出处：01 §4.1 第 2 条。

### 3.4 谓词

**形式：** 带装饰器的函数，参数是世界视图、对象和阈值，返回有符号的 margin。

```python
@predicate(desc=..., need_true=..., need_false=..., scale=...)
def near(w, g, o, max_dist=0.02):    # f(w, *对象, **阈值) -> margin [N]
    ...                               # 只经世界视图 w 和参数对象取数，算出距离 d
    return max_dist - d               # ≥ 0 表示成立
```

- margin ≥ 0 表示成立，单位由谓词说明（写在 `return` 旁的注释里）。布尔读数（如是否抓住）的 margin 取 +1 或 −1，用 `signed(flag)` 转换。谓词本身是合取时（如官方判定的两项），margin 取各项 margin 的最小值，各项先化成同一单位。margin 同时供 guidance、默认 progress 和诊断使用。
- 签名：第一个参数是 `w`；对象参数在前，没有默认值；阈值在后，默认值是数字字面量（第一层不运行代码就能与 `params` 对照）。`scale` 供默认 progress 使用（第 3.5 节）。
- 直接调用谓词时（在 progress 或别的谓词中），没有显式传入的阈值取当前生效的值：默认值，或 BO 调定的值。

**规则：**
1. **以对象为参数：** 物体只经参数进入。谓词体内不写死本任务的物体名，也不读任务特有的读数；这类读数在绑定中挂到对象上，谓词经参数读取。这样，谓词能在别的任务的状态上运行，供事后归纳词表时交叉执行。
2. **只看当前状态：** 只经适配层的世界视图读取状态，只依赖当前时刻的状态（位姿和速度都算当前状态）。不记“进入阶段时的初始距离”这类快照。
3. **同一帧的取值唯一：** 不在谓词里做滞回或平滑。
4. **一个谓词一份定义、一个阈值：** 所有实例共用。物体之间的差异写进定义，如量到物体表面或抓取点的距离，或让阈值随物体的半尺寸缩放。容差要求本身不同，就是两个条件，换名字，如 `near(g, cube)` 与 `at_goal(cube, goal)`。
5. **阈值显式声明默认值和可调范围：** 供内层 BO 使用。
6. **附一句说明：** 写明它判定的物理条件。说明须与定义相符（名实相符）。
7. **两条英文模板：** need_true 和 need_false，都写“不成立的状态，加上它的自然补救办法”，物体用显示名，显示名带冠词。占位符用谓词的参数名（如 `{g}`、`{o}`），渲染时代入显示名，句首大写。例：
   - `near(g, cube)` 需要成立：“The gripper is far from the red cube; move the gripper to the red cube.”
   - `grasped(g, cube)` 需要不成立：“The red cube is still held; release the red cube.”

**官方字段的用法：**
- 谓词一律不读 `evaluate()` 返回的字段。
- 通用函数算出的判定，作为适配层读数提供，谓词直接用。例如 Panda 的 `is_grasping(obj)` 是读数 `w.grasping(g, o)`（用它的默认参数），`grasped(g, o)` 只是把它转成 ±1。
- 要用任务特有的官方判定，就照 `evaluate()` 的源码，把公式改写成以对象为参数的谓词，并在 `official` 中声明对应哪个字段。阈值照抄官方值，固定，不放进 `params`。
- 含义不合适的官方判定，自己写谓词，不声明对应。例：StackPyramid 的“相邻”只看水平距离，把叠在一起也算进去了。
- `success` 不做成谓词，成功信号直接取环境的 success。

出处：01 §2.4、§3.2.6、§3.3 第 1、6 项、§4.1 第 5 条、§4.2、§4.3（设计规则第 5 组）。

### 3.5 progress

- 每个阶段可以有一个 progress 函数，写在 `progress.py`：`progress_<阶段名>(w, o, **params) -> [N]`，其中 `o` 是本任务绑定的对象。运行时把结果裁到 [0, 1]。
- progress 不参加词表合并，所以可以按名字读本任务的对象，也可以调用本任务的谓词。
- 只依赖当前状态和当前阶段。归一化只用固定的尺度参数（如 reach 阶段的距离尺度 d0），在 `params` 中声明默认值和范围。
- **默认 progress**（没写 progress 的阶段）：守卫中的每条文字，成立记 1，不成立记 clip(1 + margin/scale, 0, 1)，再取平均。这样，progress 与 guidance 指向同一组条件。
- **布尔条件的阶段不写 progress：** 例如守卫只有 `grasped` 的阶段，只有完成和没完成两种情况；默认 progress 在文字不成立时为 0，成立时阶段直接前进。距离类、角度类条件的阶段可以写 progress，给出阶段内的塑形。
- progress 用 `from .predicates import ...` 调用本任务的谓词与测量函数。
- 每一步对所有阶段都计算 progress（第 8.2 节的运行检查也靠这一点查出到不了的阶段里的错误），所以 progress 函数在任何状态下都要能算，谓词同理。
- **最后一个阶段：** 守卫全部成立时，progress 取 1，不论 progress 函数返回什么。这样第 4.3 节说的“成功之后 progress 为 1”对自写的 progress 也成立。
- 阶段交界处的 Φ 不要求连续，PBRS 不要求势值连续。

出处：01 §4.2。

### 3.6 绑定与世界视图

- **绑定：** `bind(env, api) -> {对象名: 对象说明}`，指明每个对象对应哪个 actor 或 site、尺寸，以及附加属性（可以是每步重读的函数）。绑定是候选中唯一能读环境内部的代码，由第一层的运行检查覆盖。
  - `bind` 以一个字典字面量返回，键与 `objects` 完全相同，第一层不运行代码就能核对。
  - 接口（M2 已实现，2026-10-26 照实际实现补全了 candidate_api.md 第 4.3、7 节）：`api.gripper()`；`api.actor(actor, half_size, **附加属性)`；`api.site(pose, half_size, **附加属性)`。site 的速度为 0，没有抓取和接触力读数。
  - 没有碰撞体的 actor（如 PickCube 的 goal_site，场景清单中标为 visual only）也可以按 actor 绑定：它的抓取读数恒为假，接触力恒为 0，适配层不向 physx 查询。
- **世界快照：** 适配层每步从环境读出一份张量快照。谓词和 progress 只读快照，不碰环境，所以保存的状态可以离线重算，谓词也能直接在别的任务的快照上交叉执行。快照包括：
  - 绑定对象的位姿、线速度与角速度、尺寸（按环境取成 [N, 3]，各并行环境可以不同），以及附加属性；
  - 夹爪的 TCP 位姿、开度、手臂关节速度，以及它对每个绑定物体的 `is_grasping`；
  - 绑定物体两两之间的接触力；
  - 带关节物体的关节读数（TurnFaucet）；没有夹爪的末端（PushT 的推杆）没有开度和“抓住”这两项；
  - `evaluate()` 返回的字段：放在快照中单独的一部分，谓词读不到，只给成功信号和 Stage2 的里程碑用。
- **统一的世界视图：** 单位是米，世界坐标系 z 轴向上，四元数顺序统一（wxyz，与 ManiSkill 相同），支撑面的顶面高度由适配层给出（`w.table_z`；ManiSkill 的桌面 z = 0）。谓词中不写死任何环境的常数。
  - 单个物体的读数放在对象视图上（`pos`、`quat`、`pose`、`lin_vel`、`ang_vel`、`half_size` 与附加属性；夹爪视图另有 `width`、`max_width`、`arm_qvel`）；两个物体之间的读数放在世界视图上（`w.grasping(g, o)`、`w.contact_force(a, b)`）。字段的完整清单见 candidate_api.md 第 4 节。
- **几何工具**（人写）：坐标变换、四元数、包围盒，如 `G.quat_to_euler_xyz`、`G.pose_inv`、`G.pose_mul`、`G.to_local`；共 12 个函数，清单见 candidate_api.md 第 4.4 节。

出处：01 §2.1、§2.2、§3.2.9 第 1 条、§3.3 第 4 项、§4.3、§4.6、§4.8。

## 4. 运行语义

### 4.1 阶段变量

- 每个并行环境有一个整数 `stage`（0 到 K−1）。它是 teacher 自己记的变量，不属于仿真器的状态。另存每条不变量的防闪烁计数。
- 正常重置时，`stage` 设为 0，GPU 并行时按 env_idx 各自重置。从中途状态开始时，设为保存时一起存下的值，不从状态推断。
- teacher 中依赖历史的只有 `stage`，即 §3.2 有意保留的“最小记忆”；Φ 只通过 k 依赖历史。

### 4.2 每一步的更新

1. 算出本步全部谓词实例的 margin 与真值。守卫、不变量、guidance 和输出都用这一份。
2. 查当前阶段的不变量：某一条不成立（m = 1，一步就算），就回退到它声明的阶段；几条同时不成立，回到其中最早的阶段。
3. 按守卫连续前进：守卫成立就进入下一阶段，接着查下一阶段的守卫，同一步可以前进几段。回退之后的同一步照样前进。
4. 按更新后的阶段，计算 p_k、Φ 和 guidance。

新进入的阶段，不变量从下一步开始检查；阶段一变，防闪烁计数清零。

例（PickCube，搬运中方块滑落）：carry 的不变量 `grasped(g, cube)` 不成立，回到 reach，同一步接着前进。
- 夹爪离方块还近：进入 grasp 后停下（`grasped` 不成立），guidance 是“抓住方块”；
- 已经远了：停在 reach，guidance 是“靠近方块”。

两种情况都对。回退目标不必选得很准，回退后由守卫自动走回正确的位置，只要回退目标选在建立被破坏条件的那一轮子目标里（第 5 节第 3 组）。

### 4.3 成功与回合结束

- 任务是否完成只由环境的 success 判定，teacher 不读 success。【事实，读 vpm-mani 中的源码】ManiSkill 每一步令 `terminated = success`（有 fail 字段时并上 fail）；官方 PPO 训练时成功即结束回合并重置，评估时忽略终止、跑到时间上限。
- 终止状态的势值取 0，成功奖励由环境给出（第 4.6 节）。
- 成功之后还继续跑的场合（评估、真机连续运行、记录过了成功点的数据）：最后一个阶段的条件就是 success，所以这时 guidance 为空、progress 为 1，与 success 一致。

### 4.4 每一步的输出

| 字段 | 形状 | 含义 |
| --- | --- | --- |
| `stage` | `[N]` 整数 | 当前阶段 k |
| `stage_progress` | `[N]` | p_k ∈ [0, 1] |
| `phi` | `[N]` | (k + p_k) / K |
| `pred` | `[N, P]` 布尔 | 文件中用到的谓词实例的真值 |
| `margin` | `[N, P]` | 各谓词实例的 margin |
| `guidance` | `[N, P]` 布尔 | 当前阶段守卫中不成立的文字 |

- 成功信号不由 teacher 给出，取环境的 `evaluate()["success"]`。
- 不输出事件：哪一步发生了回退、哪条不变量被破坏，都能从保存的阶段序列和谓词取值离线算出。
- 不输出里程碑：里程碑由适配层的通用读数计算，放在 Stage2（第 8.5 节）。
- 训练循环中不渲染文字。需要文字时，由 `guidance` 加模板生成，多条时按守卫中文字的顺序排列。
- 只算文件中用到的谓词实例；全部合法实例到 Stage3 重标时再枚举。

### 4.5 计算方式

- 测量函数、谓词、progress 和自动机更新，都写成对 `[N]` 批量张量的 torch 运算，与仿真放在同一设备上。不允许逐环境循环，也不用 `.item()`。
- Teacher 先对一批状态无状态地算出全部谓词实例，再按时间更新自动机。离线处理一整条轨迹时，N 就是帧数，谓词可以一次算完全部帧。
- 同一份代码用于 Stage2 的在线训练、Stage2 保存的 rollout 和 Stage3 的重标。

### 4.6 PBRS 奖励包装

PBRS 奖励包装属于 Stage1，是交给 Stage2 的接口：
- 奖励为 R = γΦ(s′) − Φ(s) + I_success(s′) · r_bonus，γ 与 RL 算法的折扣因子相同（§3.3 第 1 条）；
- 成功终止时，终止状态的势值取 0；超时截断不当作终止，用 critic 对最后一个状态的价值估计自举（§3.3 第 2 条）；
- 势值每一步只算一次并复用，整条轨迹上的塑形项才能逐项相消（§3.3 第 4 条）；
- 包装套在 `ManiSkillVectorEnv` 里面：先包住 ManiSkill 环境，再套 `ManiSkillVectorEnv`，与官方 PPO 的 `FlattenActionSpaceWrapper` 同一层。【事实，读 vpm-mani 中的源码】`ManiSkillVectorEnv.step` 发现回合结束，会当场重置这些环境，返回的是重置后的状态，结束前的观测另放在 `infos["final_observation"]`。包装套在它外面的话，截断那一步的 Φ(s′) 会算在重置后的状态上；
- Stage1 只做单元测试和不训练的冒烟测试（随机动作跑几个回合，至少经过一次自动重置，检查形状与逐项相消），PPO 训练归 Stage2。

出处：01 §2.2–§2.4、§4.1 第 3–7 条、§4.7。

## 5. 分解原则（TASK.md 的设计规则）

规则分两类：
- 程序能查的，写进 candidate_api.md 的静态规则，违反了第一层会报错，agent 看报错就能改（第 8.2 节）；
- 只能靠判断的，写进 TASK.md，就是下面六组。正式文件用英文。

**原理：** teacher 有 `stage` 作上下文，所以每个阶段只需回答两个问题：满足什么就前进（守卫），什么被破坏就回头（不变量）。同一个条件在别的阶段适不适用，可以不管。例：StackPyramid 放好 A 之后，`grasped(g, A)` 按计划变为不成立，但挪 C 的几个阶段只看 C 的守卫与不变量。阶段之间唯一的牵连是回退，所以回退也要保持局部（第 3 组）。

1. **阶段怎么分：** 阶段边界放在接触变化处（抓住、松开）和目标关系达成处（到达、对齐、放上）；抓取、松开各自单独成段。参照示例：reach → grasp → carry → release（第 6.4 节）。任务有几种做法时，只写最自然的一种，其他做法写进 notes.md。
2. **守卫怎么写：** 只写本段结束时必须成立、完成任务所必需的条件，通常一条。几个条件必须同时成立时才写多条，并在 notes.md 中说明理由。不为凑成一条而合成复合谓词。偏好（不是要求）：多写描述状态的条件（如 `near`：夹爪离方块近），少写一瞬间的动作（如 `gripper_open`）。
3. **不变量和回退：** 不变量只写本段内必须一直成立、一旦破坏就要回头处理的条件；有先后的条件拆成相邻阶段，前面的条件靠不变量保持（如示例中 grasp 保持 `near(g, cube)`：爪子在探索抓法时离开方块附近，就回到 reach）。回退目标选在建立这个条件的那一轮子目标里（这一轮的开头，或建立它的阶段），不回到更早的子目标。例（StackPyramid）：
   - C 掉了：回到 reach C 或 grasp C；
   - 放 C 时把 A 碰歪了：只有在 C 的几段中声明了不变量 `next_to(A, B)` 才会发现；这个条件建立于 A 那一轮，回到 reach A 重做。要不要声明这类不变量，由 agent 判断。
4. **最后一个阶段：** 守卫加不变量，合起来等于环境的 success。
5. **谓词怎么写：** 即第 3.4 节的规则 4、6、7，以及官方字段的用法。
6. **progress：** 距离类、角度类条件的阶段可以写；布尔条件的阶段不写；归一化用固定的尺度参数，在 `params` 中声明默认值和范围。

**不写进 TASK.md 的：**
- “按手段写还是按结果写”的粒度取舍：只给规则和示例，免得 agent 拿不准。
- “守卫写之后会一直成立的条件”：太严。有的条件会按计划被撤销（放好 A 后的 `grasped(g, A)`；先开后关的抽屉），有的只成立一瞬间（按按钮），这些分解都合理。

**依据（01 §4.3.1 的文献对照）：** PRM4RL、ReKep、Plan-Seq-Learn 等都把阶段边界放在接触变化或目标关系达成处，每段一个主条件，抓放类任务分 2–4 段。ReKep 的 sub-goal 约束与 path 约束，分别对应我们的守卫与不变量。

出处：01 §4.3（分解原则、TASK.md 的设计规则）、§4.3.1。

  | 1 grasp | `grasped(g, cube)` | `near(g, cube)` → reach | 布尔谓词，不写 progress；前一段的条件靠不变量保持：爪子离开方块附近就回到 reach |
  | 2 carry | `on(cube, pad)` | `grasped(g, cube)` → reach | 不变量与回退；`on` 照官方判定改写，阈值照抄，声明对应 |
  | 3 release | `not grasped(g, cube)`、`static(cube)` | `on(cube, pad)` → reach | 取反与 need_false 模板；两条文字的守卫，在 notes.md 说明理由；最后一个阶段的守卫加不变量等于 success；`Actor.is_static` |

- **不必能运行：** 谓词与 progress 只读世界视图，在合成快照上测试，示例兼作 M1 的合法玩具候选。绑定写的是虚构环境的属性；2026-10-26 照 M2 的实际接口核对过，写法不用改。
- 【事实，2026-10-21 自查，不依赖 Stage1 的代码】Python 文件能编译，YAML 能解析。草稿脚本（放在会话的临时目录，不进仓库）照第 3–5 节与第 8.2 节逐条核对，没有问题；它对 9 个故意写坏的副本都报了错。`near` 在几个手算的位置上（TCP 在方块中心、在方块一角、在顶面上方 3.4 cm 与 4 cm）与公式一致。`on`、`static` 在 2 万个随机状态上（含落在阈值上的状态）与 `evaluate()` 的公式判定全部相同。notes.md 中回退的几个例子（含 grasp 中爪子离开方块附近），用第 4.2 节的更新规则逐个推过，结果与文中一致。完整的运行验证在 M1。
- **PickCube 的参照候选：** 由人写（M3），作第一层与运行时在真实环境上的测试样例，以及 PickCube 试跑的答案；不放进任何输入包。
- 【假设】只有一个抓放示例，agent 可能把 reach → grasp → carry 照搬到推、拉、滚这类不需要抓取的任务上。第 1 组（PushCube、PullCube、RollBall）会看出来，必要时补一个推的示例。

## 7. Harness

### 7.1 调用与环境

- 代码用 `subprocess` 调用 `/home/zxh/.local/bin/claude-deepseek`（DeepSeek 版 Claude Code 的包装脚本，在项目以外；它的配置文件含密钥，不读取、不打印、不记录）。`cwd` 设为运行目录中的 `workspace/`，prompt 作为独立参数，不用 `shell=True`。
- 生成和审查都用 `deepseek-flash[1m]`（包装脚本的默认模型），不传 `--model`。v1 不用第二个 LLM 做稳健性检验。
- 子进程的环境变量由代码构造：只保留 HOME、PATH、LANG、LANGUAGE、LC_ALL、HTTP_PROXY、HTTPS_PROXY、NO_PROXY，以及 harness 为本次运行指定的 `CUDA_VISIBLE_DEVICES`，其余一概不传。

### 7.2 运行目录

每次运行一个目录 `outputs/stage1/runs/<任务>/<运行编号>/`，下分两个子目录：
- `workspace/`：agent 的工作目录（`cwd`），内容是：
  - 一份只读的输入包副本；
  - 空的 `candidate/`，供 agent 写入；
  - 固定的 `./check.sh`：不接受参数，只检查 `./candidate`，跑的就是完整的第一层（GPU、8 个并行环境），agent 写的过程中随时可以运行。
- `records/`：本次运行的记录（第 7.5 节），在 agent 能访问的范围之外。agent 有 `Write(./**)` 的许可，记录放在它的工作目录里可能被改掉。

`workspace/` 建好后 `git init`，使 agent 上下文中的 git 信息只属于这次运行。同时进行的几次生成，各占一张显卡。

### 7.3 生成会话的参数

```text
claude-deepseek -p <prompt>
  --output-format stream-json --verbose
  --max-turns <上限>
  --tools Read,Write,Edit,Glob,Grep,Bash
  --allowedTools "Write(./**)" "Edit(./**)" "Bash(./check.sh)"
  --disallowedTools WebFetch WebSearch Task
  --permission-mode dontAsk
  --strict-mcp-config --mcp-config '{"mcpServers":{}}'
  --settings '{"autoMemoryEnabled": false}'
```

- prompt 只说“先读 TASK.md”，其余文件由 agent 用工具读。
- 不加 `--no-session-persistence`，从输出中记下会话编号，供修复时续接。
- 不能写总的 `Read`、`Glob`、`Grep` 许可，否则任何文件都读得到。

### 7.4 修复与审查

- **修复：** 接着原会话，用 `--resume <会话编号>`，把第一层或第二层的报告交给 agent；限制参数每轮重新传入。
- **审查：** 另开一个独立会话，用同一模型，只给 Read、Glob、Grep，没有写入和 Bash 的许可，不能自己运行环境。

### 7.5 记录

每次运行在 `records/` 中存：输入包哈希、参数、构造出的环境变量名单（只记名字，不记取值）、CLI 版本、会话编号、每一轮的 stream-json 输出（即完整对话）、每一轮的候选与两层报告、用量、最终结论。判断成败看退出码和 `is_error`，不看 `subtype`。

### 7.6 后端、K 与冒烟测试

- 后端可替换：Claude Code 后端（接 DeepSeek）；脚本后端（直接给出参照候选，或注入典型错误），用于测试。
- K 由参数控制。
- M4 的冒烟测试就是 PickCube 试跑：端到端跑一次（agent 读输入包、写出候选、跑完两层检查）。从你的终端和从 Claude 这边各启动一次，确认两边都能登录、工具限制一致、都能走完；生成的候选与人写的参照候选逐项对比。

### 7.7 实测结论

【事实，2026-10-21 实测，Claude Code 2.1.223，共调用 11 次；原始记录在 `outputs/stage1/probe_claude_deepseek/20261021-111820/`，不进 git】
- **登录：** 从 Claude Code 的进程里启动时，会继承外层的 `CLAUDE*`、`ANTHROPIC*` 变量，返回 “Not logged in”。去掉这两类变量后成功，只保留最小环境变量也成功。
- **隔离：** 上面的参数都实测有效。`dontAsk` 模式下，凡未被允许的操作一律拒绝；`Bash(./check.sh)` 是精确匹配，带参数被拒；不写总的 Read 许可时，读和写都限于运行目录内；单独 `git init` 后，上下文中不再混入外层仓库的 git 信息；自动记忆完全关闭。
- **续接与结束：** `--resume` 有效，续接后限制依然有效；`--max-turns` 到上限后以 `error_max_turns` 结束，退出码为 1。出错时结果中也写 `subtype: success`，所以看退出码和 `is_error`。
- **没有测：** 端到端运行，留给 M4 的冒烟测试。

## 8. 检验与通过标准

### 8.1 Stage1 不用示范

所有任务都按“没有示范”处理：Stage1 只做形式检查、运行检查和代码审查；轨迹检查、回放摘要都在 Stage2 用成功的训练 rollout 做。

【事实，2026-10-21 核对，只列目录和源码，没有下载】ManiSkill 3.0.1 注册的 74 个任务中，官方示范库只有 16 个任务有示范；MetaWorld 的任务只有脚本策略，没有现成的示范文件；LIBERO 的 130 个任务都有示范。

### 8.2 第一层：程序检查

按顺序进行，前一项不通过就不往下跑。`check.sh` 跑的就是这四项。

1. **解析：** YAML 与 Python 文件能解析。
2. **schema 与引用：**
   - 文字语法正确；谓词存在，对象参数个数对得上；对象在 `objects` 和绑定中都有；
   - 回退目标在当前阶段之前；每个阶段的守卫非空；
   - `params` 的名字对得上谓词阈值或 progress 参数，默认值在范围内，且与函数签名中的默认值相同；
   - 用到的谓词都有模板，用到取反时有 need_false 模板；
   - 照官方判定改写的谓词，阈值不出现在 `params` 中；`official` 声明的格式正确；
   - 四项新检查：
     - 同一守卫中不能同时有 p 和 `not p`（这个阶段永远出不去）；
     - 不变量不能与本阶段的守卫矛盾（不变量要求 p 成立，守卫里却有 `not p`，或者反过来）；
     - 回退目标不能晚于建立那条文字的阶段：不变量的文字，必须出现在从回退目标到本阶段前一个阶段之间某个阶段的守卫里，否则回退后会一路走回本阶段，这条不变量形同虚设；
     - 最后一个阶段必须声明对应 success：`success` 一条的文字，正好是最后一个阶段的守卫文字加不变量文字。
   - 补充（2026-10-21 写 candidate_api.md 时定；都是程序能查的，按第 5 节的分工放进静态规则）：
     - 非官方谓词的每个阈值、每个 progress 参数，都要在 `params` 中声明；
     - 模板的占位符只能是谓词的对象参数名；
     - `bind` 返回字典字面量，键与 `objects` 相同；
     - 谓词与 progress 的签名照第 3.4、3.5 节，progress 的函数名对得上阶段；
     - `official` 中同一个键只出现一次；键是否真由 `evaluate()` 返回，放到运行检查中查。
3. **AST 限制：**
   - `predicates.py`、`progress.py` 只能 import torch（含子模块）、math 和 `vpmkit.api`，`progress.py` 另可 `from .predicates import ...`；不能用 `.item()`、`.tolist()`、`.numpy()`、`.cpu()`；不能有 for、while 和推导式；
   - 谓词只经参数访问物体：不能读 `.name`，世界视图也不提供按名字取物体的接口；不读官方字段；
   - 只有 `bindings.py` 能读环境；
   - 候选中所有 `.py` 文件：不许读写文件、起进程、联网，不许用 `exec`、`eval`、`__import__` 和双下划线属性。候选是 agent 写的代码，会在我们的进程里执行；谓词与 progress 已有 import 白名单，这几条主要针对 `bindings.py`。
   - 落实为：不许用 `open`、`exec`、`eval`、`compile`、`__import__`；不许 import os、sys、io、pathlib、shutil、glob、tempfile、pickle、shelve、subprocess、multiprocessing、threading、socket、urllib、http、requests、importlib、ctypes、builtins；不许出现以双下划线开头和结尾的名字或属性。这些是护栏，不是沙箱。
4. **运行检查：** 用 GPU、8 个并行环境、3 个随机种子，各走 30 步随机动作（约 744 个状态）。全部谓词实例、各阶段的 progress 和自动机更新都不报错，形状为 `[N]`，没有 NaN 或 Inf。
   - 目的：确认候选在真实环境中、按 Stage2 训练时的方式（批量、GPU）能算出来。并行环境查批量与设备上的错误，多个种子查不同的初始布局，随机动作查运动后的状态（速度类谓词、距离为 0 时的除法等）。
   - teacher 每一步都算全部谓词和所有阶段的 progress，所以随机动作到不了的阶段，代码错误也能查出。
   - 它不检查含义。

每条规则都有错误代码（共 34 个：解析 3、schema 21、AST 5、运行 5），清单在 candidate_api.md 第 9 节。

### 8.3 第二层：审查 agent

- **什么时候跑：** 每一轮中，第一层全部通过后才跑；第一层没过，就直接把第一层的报告交回修复。
- **读什么：** 整个输入包、候选的全部文件（含 notes.md）、第一层的报告。Stage1 没有回放摘要。
- **逐项提问：**

  | 类别 | 严重程度 | 问什么 |
  | --- | --- | --- |
  | a. 官方对应 | 错误 | 每条 `official` 声明，把谓词代码与 `evaluate()` 的源码逐项对照：阈值、距离是三维还是只算水平、参考点、坐标系、是否取绝对值、合取的各项有没有漏；最后一个阶段的守卫加不变量是否正好等于 success |
  | b. 名实相符 | 错误 | 每个谓词的说明与代码是否一致 |
  | c. 能否完成 | 错误 | 照这条链走下去，能否达到环境的 success（如 StackCube 漏了松手） |
  | d. 回退 | 错误 | 回退目标是否回到了更早的子目标 |
  | e. 挡住正常做法 | 错误 | 守卫是否会挡住正常的做法（如阈值比抓取实际需要更严的 `gripper_open`） |
  | f. 粒度 | 提醒 | 可以合并的阶段、可有可无的守卫文字；多条文字的守卫是否在 notes.md 中说明了理由 |
  | g. 模板 | 提醒 | 是否“状态加补救办法”，显示名是否带冠词 |
  | h. progress | 提醒 | 距离类、角度类的阶段有没有合适的 progress，尺度参数是否声明 |
  | i. 阈值 | 提醒 | 默认值与范围是否合理 |
  | j. 其他做法 | 提醒 | 其他做法是否写进 notes.md |

- **输出：** JSON 列表，每条含类别、严重程度、位置（文件与行，或 YAML 中的路径）、问题、建议的改法。
- **报错误的门槛：** 报“错误”必须引用能证明它的代码行（a 类还要引用 `evaluate()` 中对应的行）；a–e 类中拿不准的问题，严重程度降为“提醒”，不挡住候选。f–j 类一律是提醒。表中各类的严重程度，指的是有把握时。
- **只报上面的类别：** 这些类别以外的问题一律不报。
- **提示词：** 2026-10-26 写好，放在 `vpmkit/resources/review_prompt.md`（英文；第一层的报告和上一轮报的错误由 harness 填入）。
- **提醒：** 只记录；这一轮本来就要修复时，与错误一起交回。
- **有分歧时：** 生成 agent 认为某条错误判错了，可以不改，但要在 notes.md 中写明理由；下一轮的审查看到理由后可以撤回。

### 8.4 门槛、轮数与人工介入

- **进入 Stage2 的门槛：** 第一层四项全部通过，且第二层没有“错误”；有“提醒”也可以通过。
- **轮数：** 首次生成算第 1 轮，之后最多修复 3 轮，一次运行最多 4 轮。agent 结束本次回答、用完 `--max-turns` 或到达本轮的时间上限，这一轮就结束；harness 随即对当时的候选跑第一层，通过后再跑第二层。
- **成败按次运行统计：** 第 4 轮后仍未通过，记为这次运行失败。每次运行记下用了几轮、每一轮各类错误各几条，Stage1 的错误率和 G1 由此计算。
- **人工介入按任务计：** 一个任务的 K 次运行只要有一次通过，就不需要人出手；全部失败时，由人从错误最少的那次运行出发，修到能通过，记为一次人工介入，并保存修改的 diff 与理由。
- **harness 自身的故障**（DeepSeek 接口出错、请求超时、审查输出的 JSON 解析不了）不算候选失败：最多重试 2 次，仍不行就把这次运行记为“harness 故障”，单独列出，不计入错误率。
- 通过的候选全部交给 Stage2，怎么选在 Stage2 定。

### 8.5 留给 Stage2 的

下面这些都要在 rollout 上计算。Stage1 没有成功轨迹，算不出结果，所以和 Stage2 一起设计、一起实现：
- 守卫的必要性与充分性；
- 预测性：只用标量进度，对比进度加谓词向量，预测随后的失败或卡住；
- 阶段是否只由当前状态决定；
- 链覆盖率（与轨迹检查合为一项）：成功回合中，成功时已到最后一个阶段、中途没有回退的比例，以及守卫文字在成功回合上是否为常数；
- 零步阶段（可以合并的信号）；
- 给第二层审查的回放摘要：阶段转换的时刻、卡在哪个谓词上、离阈值差多少、阶段交界处 Φ 跳变的大小；
- Stage2 早期评价用的里程碑：由适配层的通用读数计算，与候选无关。读数包括 `evaluate()` 返回的布尔字段；每个动态物体的“被夹爪抓住”“比重置时高出 2 cm 以上”“被推动”（离开重置位置超过一定距离）；“关节被转动”。阈值在 Stage2 定。

“一致性”由结构保证，不另行检验；“可执行性”v1 不做。Stage1 不需要为这些额外准备：teacher 每一步的输出，以及在保存的状态上离线重算，已经够用。

出处：01 §3.3 第 3 项、§4.5、§4.6。

## 11. 主要取舍与理由

**表示**

1. **候选是声明式的 Stage Graph 文件，加少量受限的 Python。**
   - 不采用：整个 teacher 写成一段自由代码；整个候选写成受限的 Python DSL。
   - 理由：内层 BO 需要显式的参数空间，外层由 LLM 改结构；用声明式文件，这两件事都变成对数据的编辑，“增删守卫文字”“拆分阶段”也能作为离散操作记录下来。schema 检查、guidance 的派生、阶段等权的 Φ，都能对文件机械地完成；写成自由代码，这些只能靠解析代码或在运行时探测。代码只经世界视图读状态（AST 检查保证），所以同一份代码能离线运行在保存的状态上，换仿真器时也不用改。
2. **谓词由 agent 逐任务编写，不建共享谓词库，不用类型标签。**
   - 不采用：人建带类型签名的共享库，LLM 只从中选。
   - 理由：人建的库是一种任务先验，把“自动构建”的一部分工作转给了人；agent 有完整的 harness，能读源码、写代码、运行，只在库里选谓词，这些能力用不上；G1 两侧都由 agent 写，差别只在表示。跨任务的一致性，由事后归纳的共享词表处理（§3.7）。
3. **一个 teacher 是一条线性链。**
   - 不采用：分支图。
   - 理由：Φ = (k + p_k)/K 要求阶段排成全序，分支上各条路径长度不同，Φ 在路径之间不可比；分叉点上有几组守卫，说不清 guidance 该提示哪一组；检查和 Stage2 的结构编辑都在一条链上做，简单。
4. **有几种做法时，只写最自然的一种。**
   - 不采用：在一张图里写出多种做法。
   - 理由：“多种做法”分三种。同一做法内部的变化（抓的位置、掉了重抓），由“守卫只规定条件”和回退处理；顺序无所谓的子目标（LIBERO），以后用“并列”组合处理；真正不同的做法（如 StackPyramid 挪 A 还是挪 B）原则上数不完，在图里比较两条路要靠 Φ 的刻度，两条路不对称时不可比，放在候选之间则靠成功率和样本效率比较，天然可比。按 PBRS，塑形不改变最优策略，只写一种做法的代价在学习效率上。论文中的说法是“在试过的做法里选最好的”。
5. **守卫是文字的合取，文字可以取反，没有“或”。**
   - 不采用：允许“或”；为“没被抓住”另写反义谓词。
   - 理由：合取时“还差哪些条件”的答案唯一，guidance 清空、守卫成立、阶段转换是同一件事；官方成功判定里本来就有取反（StackCube 要求红块没被抓住）；取反与原谓词恰好互补，反义谓词各有阈值，在阈值附近可能同时成立或同时不成立。
6. **阈值按谓词，不按实例。**
   - 不采用：每个实例各设阈值。
   - 理由：一个名字一种含义，第二层才好核对说明与定义；共享词表的一个编号要有一致的含义；内层 BO 的参数个数与按实例时相同。
7. **谓词不读官方字段；要用官方判定，就照公式改写、声明对应，阈值固定。**
   - 不采用：谓词直接读 `evaluate()` 的字段。
   - 理由：直接读官方字段的谓词离不开本任务，在别的任务的状态上跑不了，参加不了交叉执行；改写后只剩一条规则（谓词只经参数读状态），AST 检查就能保证；阈值固定，Stage2 调参后才不会出现 teacher 判“到了”、环境判“没到”。
8. **谓词与 progress 只看当前状态，不记快照。**
   - 不采用：记下“进入阶段时的初始距离”这类快照，用来归一化。
   - 理由：快照会让同一帧的标签依赖历史，视觉 VPM 学不到，也会干扰“阶段是否只由当前状态决定”的检查；归一化改用固定的尺度参数，交给内层 BO 调。【事实，据 PRM4RL 精读笔记，没有重读原文】PRM4RL 附录 A.6 的公开示例中，进度错误就出在归一化的基准距离取错（接近阶段的进度恒为 0），以及到达目标时势值反而下降。

**运行语义**

9. **图中没有完成节点，成功由环境判定。**
   - 不采用：最后一个守卫成立就进入完成节点；完成节点跟随环境的 success。
   - 理由：前者在 teacher 判完成、环境却未判成功时，Φ = 1、guidance 为空，策略在没做完时失去指引；后者让视觉 VPM 多学一个“完成”类，实际是在学成功检测，与“成功信号独立判定”（§3.3 第 3 条）冲突。不设完成节点最简单，teacher 只描述过程；“最后一个阶段等于 success”的要求，消除了成功之后继续跑时的不一致。
10. **m = 1，谓词不做滞回，不做闪烁统计。**
    - 不采用：不变量连续 2 步不成立才回退；在谓词里平滑。
    - 理由（你的意见）：守卫要精准，teacher 如实记录仿真中的真实情况；某个谓词闪一帧却不代表真的掉了，说明它的定义或阈值没有表达出想要的概念，应修谓词，防闪烁反而会掩盖这类问题。同一帧的取值唯一，交叉执行和 Stage3 的标签也需要这一点。代价很小：回退后同一步照样前进，不会卡住。
11. **teacher 不输出事件。**
    - 不采用：不变量被破坏时附一条事件说明（如“方块掉了”）。
    - 理由（你的意见）：事件是跨时间步的描述，而 teacher 的输出都针对一个时间步；回退后的 guidance 已给出要做的事；需要时，可以从保存的阶段序列离线算出。
12. **回退后同一步照样前进。**
    - 不采用：回退的这一步不再前进。
    - 理由：回退目标不必选得很准，由守卫自动走回正确的位置；不前进的话，会出现“方块就在手里，guidance 却是靠近方块”的一帧。

**输入与检验**

13. **源码删去两个奖励函数。**
    - 理由：ManiSkill 的稠密奖励本身就是分阶段写的，留着 agent 很可能照抄，“自动构建”名不副实，结果也会与“环境稠密奖励”基线几乎重合。
14. **示例用虚构的典型抓放任务，不取自评测任务；16 个任务都生成。**
    - 不采用：PickCube 作示例（10-21 原定，它的参照候选反正要写，但最常用的任务因此退出比较）；留一法，即再写一份参照候选，生成那两个任务时互换示例（多写一份，且这两个任务看到的示例与其余不同）；刻意避开与评测任务相似的冷门场景。
    - 理由（你的意见）：PickCube 是大家公用的环境，拿它当示例，能比较的实验就少一个；机器人任务本来相通，示例不用刻意避嫌。示例的作用是教格式、定分寸、示范从源码到候选的对应，所以按示范价值选：典型的抓放任务覆盖的机制最多，还能示范 PickCube 示范不了的取反。
15. **Stage1 不用示范。**
    - 理由：扩展任务时，大多数任务没有示范（ManiSkill 74 个任务中 16 个有）；统一不用，各任务的检查口径一致。
16. **不逐帧核对官方对应，由第二层对照源码核对。**
    - 不采用：第一层在本任务的状态上逐帧核对（一致率 ≥ 99.5%）。
    - 理由（你的意见）：输入包提供了 `evaluate()` 的源码、类外辅助函数和属性的实际值，读代码就能核对。另外，Stage1 的随机动作很少触发 success 一类字段，逐帧核对多半是“未覆盖”。漏过的错误由 Stage2 的统计发现（第 12 节）。
17. **`check.sh` 跑完整的第一层。**
    - 不采用：自查只跑静态检查和 CPU 单环境的运行检查。
    - 理由：自查与最终判定是同一套检查，不会出现“自查通过、提交后不通过”；只在 N > 1 时暴露的形状问题、各并行环境尺寸不同、新建的张量没放到 GPU 上，都能提前查出，否则要到 Stage2 训练时才暴露。代价：每次自查启动一次 GPU 仿真（几十秒），同时进行的几次生成各占一张卡。
18. **基于 rollout 的检验和里程碑放在 Stage2。**
    - 理由：Stage1 没有成功轨迹，这些检验算不出结果；它们的输入格式取决于 Stage2 的 rollout，输出也主要给 Stage2 的外层用。里程碑要对所有候选相同（§4.4），取自某个候选的谓词，评价别的候选时不公平；用通用读数，不需要逐任务的人工，判定也可靠。

**Harness**

19. **子进程的环境变量由代码构造。**
    - 不采用：继承调用方的环境。
    - 理由（你的意见）：关键是代码启动时的环境，而不是谁来启动。实测中，从 Claude Code 里启动会继承外层的变量，导致 “Not logged in”；由代码构造，谁启动结果都一样。

出处：01 §2.1、§2.4、§3.4、§4.1–§4.6。

## 12. 待定事项、假设与风险

**【待定】以后再定的：**
- G1 的对照设计：两侧怎样对齐、是否加“一次生成”的 2 × 2 设计、K、错误分类、人工抽查。先实现我们自己的方法再定，这一轮不写 G1 的代码。
- 输入包生成程序会在三个任务上报错停下（第 6.2 节），到 M4a 时由你决定怎么处理：PullCubeTool 的 `evaluate()` 自带 `reward` 与进度公式；TurnFaucet 有注释掉的稠密奖励；PushT 的成功判定函数里有名为 `reward` 的变量。
- Stage2 设计时定：是否主动让 agent 写出不同的做法；多个通过的候选怎么选；通用里程碑的阈值；rollout 的保存格式（§6.4）；Stage2 外层能否引入或修改谓词（§9 第 17 项）。
- 做 LIBERO 之前：顺序无所谓的子目标要用“并列”组合（几条线性链同时跟踪），它的 Φ、选择点上的 guidance、跨子链的不变量，要专门设计。
- 扩展到 MetaWorld 时：跨仿真器兼容的其余三条原则（测量量的供需对得上、物体之间的差异放进对象属性、跨仿真器比对）；示例的环境源码与绑定按 MetaWorld、LIBERO 改写。
- 论文是否保留可执行性检验（§9 第 15 项）。
- `is_grasping` 按接触力判定，在图像中看不见，作为 Stage3 的标签不易学；v1 先允许用，合并词表时再处理。

**【假设】要实测的：**
- teacher 的批量计算不会成为训练的瓶颈。
- 提供几何工具，能减少 DeepSeek 在四元数、坐标变换上的低级错误。
- 一个抓放示例够用：agent 不会把抓取的结构照搬到推、拉、滚类任务上（第 6.4 节）。
- 短训练能分辨做法的好坏（E-S3）。

**风险：**
- 6 个任务没有官方 PPO 配置，要自己调超参数；回合上限 200–250 步的 4 个任务，即使塑形做得好，也可能在预算内训不出来。
- 第二层靠读代码核对官方对应，可能看漏细节，例如 StackCube 的 `is_static` 传入 `ang_thresh=0.5`（默认值是 0.1）、StackPyramid 的 `abs(dz) > 0.02`、PegInsertionSide 要先变换到孔的坐标系。漏过的错误会表现为：成功时 teacher 还没到最后一个阶段，或最后一个阶段的条件都已成立却迟迟不成功；由 Stage2 的链覆盖率等统计发现。

## 附录 A. 名词

| 名词 | 含义 |
| --- | --- |
| 过程 teacher | 一个任务的 Stage Graph 加各阶段的 progress。读特权状态，逐步给出阶段、进度、Φ、谓词取值与 guidance |
| 候选 | agent 写出的一个过程 teacher，即一个候选目录 |
| 示例 | 输入包中给 agent 参考的虚构抓放任务：虚构的环境源码加完整的候选，所有任务看到同一份（第 6.4 节） |
| 参照候选、PickCube 试跑 | 参照候选是人写的 PickCube 候选，作测试样例和试跑的答案，不进输入包；试跑是先在 PickCube 一个任务上走通全流程（包括生成），再扩展到其余 15 个 |
| 谓词、谓词实例 | 谓词是以对象为参数的判定函数，如 `near(g, o)`；代入本任务的对象就是实例，如 `near(g, cube)` |
| 文字 | 一个谓词实例，或它的取反 `not p(...)` |
| 守卫 | 一个阶段结束时必须同时成立的文字；全部成立，就进入下一阶段 |
| 不变量、回退目标 | 不变量是本阶段内必须一直成立的文字；它不成立时，回到回退目标指定的更早阶段 |
| margin | 谓词返回的有符号数：≥ 0 表示成立，数值表示离阈值还差多少 |
| guidance | 当前阶段守卫中不成立的文字，用模板渲染成英文提示 |
| Φ（势值） | (k + p_k)/K：k 是当前阶段，p_k 是阶段内进度，K 是阶段数 |
| 官方对应 | 候选中声明的“一组文字的合取 ↔ `evaluate()` 的一个键” |
| 输入包 | 每个任务一份、由程序生成的文件夹，是 agent 能看到的全部材料 |
| 运行目录 | 一次运行的目录：`workspace/` 是 agent 的工作目录（输入包副本、`candidate/`、`check.sh`），`records/` 放记录 |
| 运行、轮 | 一次运行是把生成流程从头跑一遍，最多 4 轮；一轮是 agent 的一次作答（首次生成或一次修复），之后跑两层检查 |
| 第一层、第二层 | 第一层是四项程序检查，作为硬门槛；第二层是只读的审查 agent |
| 人工介入 | 一个任务的 K 次运行全部失败时，由人修到通过 |
| 链覆盖率 | 成功回合中，成功时已到最后一个阶段、中途没有回退的比例（Stage2 计算） |
| 里程碑 | Stage2 早期评价用的固定指标，由适配层的通用读数计算 |
