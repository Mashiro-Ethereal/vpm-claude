### 1.2 对 Stage1 的理解（2026-10-19 复述，你未提出异议；2026-10-20 按第 2 点的结论修订）

2026-10-19 的复述原文见提交 057e6a1。修订的是“表示”“分工”“检验”“范围与实验”四条中按人建谓词库写的内容。

- **定位：** Stage1 把一个任务的过程知识自动写成程序，即过程 teacher 的初始候选。程序读仿真特权状态，可以逐步执行。
  - 语义是否正确、进度是否好用，由 Stage2 用特权状态策略的训练反馈来检验和修正。
  - Stage1 要保证三点：派生产物一致；能在实际环境中运行；结构和参数可以分开修改，方便 Stage2 的两层搜索（§3.1、§3.6、§4.2）。
- **表示：** 过程 teacher 由 Stage Graph 和阶段内 progress 组成。
  - Stage Graph 是带守卫谓词的阶段自动机：节点是阶段；前向边上的守卫是谓词的合取；每个阶段标明需要保持的不变量，不变量被破坏时，沿回退箭头回到能重新建立它的阶段。
  - 谓词由 agent 为每个任务编写：以对象为参数，只经统一的世界视图读取当前状态，附阈值（默认值与可调范围）、模板和一句说明。不用类型标签，也不用共享谓词库；跨任务的一致性由事后归纳的共享词表处理（本文 §3.3 第 1 项）。
  - 三种输出出自同一结构：阶段；势值 `Φ = (k + p_k(s; θ_k)) / K`；guidance，即当前阶段出边守卫中不成立的谓词，用模板渲染，不变量被破坏时另附一条事件说明（§3.2–§3.4、§3.7）。
- **分工：**
  - 人：每个仿真器做一次与任务无关的基础设施，即适配层和通用几何工具（本文 §3.3 第 4 项）。
  - agent（LLM 用 DeepSeek，Harness 用 Claude Code，§9 第 1 项）：为每个任务编写对象绑定和任务特有的几何、测量函数、谓词、Stage Graph 和 progress。
  - 经过：原设计由人建带类型签名的共享谓词库，新谓词先作为任务局部谓词，被多个任务用到后再升入共享库；2026-10-19 曾改为“谓词库覆盖全部计划任务、LLM 只用库中的谓词”，同日改为由 agent 编写（本文 §3.2.1、§3.4）。
- **检验：**
  - 两层 validator：第一层是程序检查，作为硬门槛；第二层是审查 agent，判断语义是否合理（本文 §3.3 第 2 项）。报告的问题交给编写的 agent 修复，轮数有上限。
  - 五项语义检验：必要性与充分性、可执行性、预测性、一致性、阶段是否只由当前状态决定。其中可执行性检验 v1 不做（本文 §3.3 第 3 项）；需要“保存的 rollout”的几项，Stage1 只能先用示范做一部分，完整版要等 Stage2（§3.5、§6.4）。
- **范围与实验：**
  - 任务：ManiSkill 的 PickCube、LiftPegUpright（第一层），以及 StackCube、PegInsertionSide、StackPyramid（第二层）。
  - 实验：G1（两侧都由 agent 编写，只比较表示）和共享词表的对比实验（§6.2）。增长曲线 2026-10-19 起不再作为主线实验。
  - 下游对 teacher 的三项硬要求：
    - 作为奖励时，满足 §3.3 的六条规则；
    - 能在 GPU 上对全部并行环境批量计算（由 §6.3 的 GPU 并行 PPO 推出）；
    - 能在保存的状态上重放，供 Stage3 重标（§5.2）。

## 2. 第 1 点：产物形态与运行时接口（已定，2026-10-19）

### 2.1 产物形态【决定】

每个候选是一个目录，由一个声明式的 Stage Graph 文件和少量受限的 Python 代码组成：

- `stage_graph.yaml`：对象及其绑定（任务特有的读数在这里挂到对象上）、阶段列表、出边守卫、不变量及回退目标、guidance 的排序、谓词实例与官方字段的对应声明（本文 §3.3 第 6 项），以及全部可调参数（名称、默认值、范围）；按 schema 校验。
- `predicates.py`：该任务的测量函数和谓词，由 agent 编写，放在该任务的候选目录中，任务之间不共用（本文 §3.3 第 1 项）。原设想的 `local_predicates.py`（任务局部谓词）随共享谓词库一起取消。
- `progress.py`：各阶段的 progress 函数。

示意如下，以 PickCube 为例（本文 §3.3 第 6 项）。格式细节在第 5 点定。

```yaml
objects:          # 显示名用于模板；与仿真物体的绑定略
  g:    {name: the gripper}
  cube: {name: the red cube}
  goal: {name: the goal}
stages:
  - name: reach
    exit: [gripper_open(g), near(g, cube)]
  - name: grasp
    exit: [grasped(g, cube)]
  - name: carry
    invariants: [{pred: grasped(g, cube), regress_to: reach, event: cube_dropped}]   # 回退的语义在第 3 点定
    exit: [at_goal(cube, goal)]
  - name: settle
    invariants: [{pred: at_goal(cube, goal), regress_to: carry}]
    exit: [arm_static(g)]
official:         # 照官方判定改写的谓词实例，由第一层逐帧核对
  at_goal(cube, goal): is_obj_placed
params:           # 内层 BO 的搜索空间；照官方判定改写的阈值固定，不在这里
  - {name: near.g_cube.d, default: 0.02, range: [0.01, 0.05]}
```

理由：
- 【推导】内层 BO 需要显式的参数空间，外层由 LLM 改结构。用声明式文件，这两件事都变成对数据的编辑：BO 只改参数段；外层的“增删守卫谓词”“拆分阶段”可以作为离散操作记录下来，E-S1 统计错误类型时也方便。
- 【推导】schema 检查、guidance 派生、阶段等权的 Φ，都能对文件机械地完成。如果整个 teacher 是一段自由代码，这些只能靠解析代码或在运行时探测。
- 【推导】G1 比较的是“带守卫谓词的自动机”与“自由代码”，两侧都由 agent 编写，所以我们这一侧的产物本身就应当是组合式的。

“受限”的含义：
- 谓词、测量函数和 `progress.py` 只能通过适配层的世界视图读取状态，谓词还只能经参数访问物体（本文 §3.3 第 1 项的要求 2），都不能直接读仿真器内部，用 AST 检查保证。好处有三：同一份代码能离线运行在保存的状态上；换仿真器时不用改；以后落实 §7.3 的“progress 只用可观测的测量函数”也容易。
- 直接读仿真器内部的只有对象绑定这一处，由第一层的运行检查覆盖（本文 §3.3 第 2 项）。

2026-10-20 按第 2 点的结论修订：去掉类型标签；`local_predicates.py` 改为各任务的 `predicates.py`；示例改为 PickCube，并加入官方字段的对应声明。

备选（未采用）：整个候选写成受限的 Python DSL。它的好处是 G1 的两侧都是 Python，比较时不混入文件格式的差别。采用声明式文件后，两侧的文件格式不同（YAML 加代码，对比纯代码），这一点在第 8 点讨论 G1 的对照设计时处理。

### 2.2 运行时【决定】

- 测量函数、谓词、progress 和自动机更新，都写成对 `[N]` 批量张量的 torch 运算，与仿真放在同一设备上，不允许逐环境循环，也不用 `.item()`。示范、Stage2 保存的状态和 Stage3 重标都走同一份代码，离线处理时 N 就是帧数。
  - 【事实】ManiSkill 官方 PPO 配置用 2048–4096 个 GPU 并行环境（[对话总结](../00_conversation_digest.md) §5.2）。
  - 【假设】teacher 如果逐个环境用 Python 计算，会成为训练瓶颈；开销需要实测。
- 代码分三层：
  1. **适配层**（每个仿真器一个，由人写）：从特权状态读出通用物理量，如物体位姿与尺寸、速度、TCP 位姿、夹爪开度、两两接触力；通用函数算出的判定（如 Panda 的 `is_grasping(obj)`、`is_static`）也作为读数提供。`evaluate()` 字段另行提供，只给 validator 和成功信号用（本文 §3.3 第 6 项）。
  2. **测量函数、谓词与 progress**（每个任务由 agent 写，与仿真器无关）：只通过适配层的世界视图取数。
  3. **自动机运行时**（与仿真器无关，由人写）：读 Stage Graph 文件，跟踪阶段，计算 Φ 和 guidance。
- 【推导】扩展到 MetaWorld、LIBERO 时，只需新写适配层。跨任务的一致性由事后归纳的共享词表处理；跨仿真器合并，要求各适配层的世界视图单位和坐标系一致（本文 §3.3 第 1 项）。
- 2026-10-20 按第 2 点的结论修订：原第 2 层是共享的谓词库，现为各任务自己的谓词。

### 2.3 每一步的输出【决定】

| 字段 | 形状 | 含义 |
| --- | --- | --- |
| `stage` | `[N]` 整数 | 当前阶段 k |
| `stage_progress` | `[N]` | p_k ∈ [0, 1] |
| `phi` | `[N]` | (k + p_k) / K |
| `pred` | `[N, P]` 布尔 | 文件中用到的谓词实例（守卫、不变量、里程碑）的取值 |
| `margin` | `[N, P]` | 有符号的“离阈值还差多少”，例如 `near` 取 d_max − d；供分级谓词、progress 和诊断使用 |
| `guidance` | `[N, P]` 布尔 | 当前阶段出边守卫中不成立的谓词 |
| `event` | `[N]` 整数 | 本步是否有不变量被破坏，回退到哪个阶段 |
| `milestone` | `[N, M]` 布尔 | 固定里程碑的取值，供 Stage2 早期评价（第 8 点） |

- 成功信号不由 teacher 给出，取环境的 `evaluate()["success"]`（§3.3 第 3 条）。
- 训练循环里不渲染文字；需要文字时，再由 `guidance` 加模板生成。
- §5.3 要求视觉 VPM 预测“每个合法谓词实例”。Stage1、Stage2 只算文件中用到的实例，全部合法实例等 Stage3 重标时再枚举，以节省训练时的计算。

### 2.4 状态依赖【决定】

- 谓词和 progress 只依赖当前时刻的完整物理状态，位姿和速度都算当前状态。不记录“进入阶段时的初始距离”这类快照；归一化用固定尺度参数，交给内层 BO 调（细节在第 4 点）。
- teacher 中依赖历史的只有自动机的当前阶段，这是 §3.2 有意保留的“最小记忆”。所以 `Φ = (k + p_k(s)) / K` 只通过 k 依赖历史。
- 每个环境记一个当前阶段（以及第 3 点要定的防闪烁计数），环境重置时按 `env_idx` 重置。
- 理由：
  - 【事实，据 [PRM4RL 精读笔记](../../references/notes/base_progress_reward.md)“限制”第 2 条，没有重读原文】PRM4RL 附录 A.6 的公开示例中，进度错误出在两处：归一化的基准距离取错，使接近阶段的进度恒为 0；到达目标时势值反而下降。
  - 【推导】快照会让同一帧的标签依赖历史：视觉 VPM 学不到，也会干扰“阶段是否只由当前状态决定”这项检查。

### 2.5 交付物与生成次数【决定】

- **基础设施（做一次）：** 适配层、自动机运行时、两层 validator 与语义检验、生成 harness。原先还列有“谓词库及单元测试”；2026-10-19 改为由 agent 编写谓词后去掉（本文 §3.4）。
- **每个任务：** 通过 validator 的初始候选，附生成记录和检验报告。
- **生成次数：** “K 次独立生成”就是把同一个生成流程独立跑 K 次，每次从头开始，只有采样的随机性不同。
  - 先把一次生成写好，K 留到第 8 点（G1）再定。
  - 实现上要求每次运行有独立的目录和完整记录，以后重复多次时不用改代码。
- 【推导】K > 1 以后有两个用处：
  - G1 需要错误率的分布，而 PRM4RL 没有报告生成可靠性（精读笔记“限制”第 3 条）；
  - Stage2 需要初始候选。

## 3. 第 2 点：谓词库 v1 与 ManiSkill 适配层（已定，2026-10-20）

### 3.0 已认可：哪些必需，哪些不必承诺【决定，2026-10-19】

讨论缘起：你担心同一个谓词在不同环境中的表示方法不同，最后做不出来。你认可了以下划分：

- **必需：谓词化的表示本身。** guidance、守卫、内层 BO 的参数空间、Stage2 的里程碑、V0 的谓词向量、Stage3 的谓词输出，都建立在它上面。
- **必需：同一仿真器内跨任务共享。** 视觉 VPM 共享输出头、LIBERO-10 的组合泛化，都依赖这一点。它的成本很低：每个仿真器只有一个适配层，谓词只写一份。
  - 2026-10-19 补记：改为构建时不共享，各任务的谓词独立编写；跨任务共享推迟到 Stage3 之前，由事后归纳的词表提供（本文 §3.3 第 1 项）。
- **不必承诺：跨仿真器共用同一份定义。**
  - 它支撑两件事：贡献 1 中“可复用”的更强说法；§5.2 设想的用一个视觉 VPM 覆盖全部任务。
  - 某个谓词在别的仿真器里保持不了原来的含义时，按“同名必同义”换个名字。视觉 VPM 照样能训练，标签也不会出错，只是共享的部分少一些。
  - 所以这部分失败的后果是“共享程度低于预期”，而不是“做不出来”。
- 【事实】VPM_idea 本来就把复用当作可能失败的实验问题：
  - §3.7 写明，增长曲线“不变平，则说明方法的适用范围有限”；
  - [对话总结](../00_conversation_digest.md) §8 把“G1 与谓词库增长曲线”列为决定后续走向的经验关口之一。
  - 以上是 2026-10-19 修改前的写法。修改后，增长曲线不再作为主线实验，见本文 §3.2.1。

另有三点：
- Panda 的 `is_grasping(obj, min_force=0.5, max_angle=85)` 要求两指与物体的接触力都 ≥ 0.5 N，且力的方向与手指张开方向的夹角 ≤ 85°。PegInsertionSide 自己的稠密奖励改用了 max_angle=20。
- `Actor.get_collision_meshes()` 在 CPU 上计算，没有缓存，也不支持合并后的 Actor，所以取不到 PegInsertionSide 插销和盒子的碰撞网格。
- 桌面高度 z = 0。

对设计的影响：
1. 【推导】`evaluate()` 是成功判定，不是谓词库。StackPyramid 的“相邻”把叠在一起也算进去，“在上面”不分上下。我们的谓词要有自己的语义；与 `evaluate()` 字段比对只作为合理性检查，不当作真值。（2026-10-20 补记：官方字段的现行用法见本文 §3.3 第 6 项。）
2. 【事实】文档与代码又多了一处不一致（LiftPegUpright），此前已知 PegInsertionSide 有一处（对话总结 §5.2）。PickCube 不要求松手，LiftPegUpright 要求立在桌上，这两点也都和 §3.2 抓放例子的模式不同。这些都支持第 5 点给 LLM 源码，而不只给文档。
3. 【推导】物体尺寸要按环境取成 `[N, 3]` 张量，从环境属性（如 `peg_half_sizes`）绑定，不能依赖碰撞网格。

#### 3.2.2 类型标签与适配层

- **类型标签（可多重）：** 共六个：
  - `end_effector`；
  - `graspable`；
  - `support`：桌面，以及可以在上面放东西的方块；
  - `region`：无碰撞的目标区域；
  - `axial`：有主轴的物体，如插销；
  - `receptacle`：带孔、可供插入的物体，如 PegInsertionSide 的盒子。

  例如，StackCube 的绿块同时是 `graspable` 和 `support`。
- **适配层提供的量：**
  - 每个绑定的对象：位姿、线速度与角速度、半尺寸 `[N, 3]`，以及按类型需要的属性：`axial` 的主轴和头部位置，`receptacle` 的孔位姿与孔半径，`region` 的区域半径；
  - 夹爪：TCP 位姿、两指间宽度、指垫位姿、手臂关节速度；两指与物体的接触力只在用到时才算；
  - 桌面：作为一个 `support` 对象，顶面 z = 0。
- **几何量：** 最低点、顶面高度等，都由位姿和半尺寸按有向包围盒计算，物体倾斜时也成立。
- **与 §3.7 的差别：**
  - §3.7 的例子中，“支撑面或目标区域”是一个标签。这里拆成 `support` 和 `region`，因为 PickCube 的目标是空中的一个点，没有顶面，`on` 无法定义。
  - 另外新增 `axial`（供 `upright`、`coaxial`、`inserted` 使用）和 `receptacle`（供 `coaxial`、`inserted` 使用）。
  - 这两处都是对 §3.7 示例的细化，不改动设计。
- **v1 的范围：** 只考虑 Panda 和自上而下的抓取。
  - 【事实，据源码】五个任务的默认机器人都是 Panda。其中 StackCube、PegInsertionSide、StackPyramid 默认用 panda_wristcam，机械臂和夹爪相同，只多一个腕部相机。
  - 适配层的夹爪几何按 Panda 写；`aligned` 只比较水平面内的朝向。
  - LiftPegUpright 的抓法是否属于自上而下，要看了示范再确认。

- **`on`、`above` 改为“投影重叠”：** 原先要求 o 的中心投影落在 t 的顶面内。但在 StackPyramid 中，蓝块同时压在红块和绿块上，它的中心会落在两块交界附近，原定义可能判为不成立。重叠量沿两中心连线的方向，按有向包围盒计算。

`near` 的定义在 2026-10-19 作了修改：
- **原先的建议：** “抓取点默认取中心，可在绑定中给偏移”。这会让 `near(g, o)` 的含义随任务的绑定而变，正是 §9 第 5 项担心的情况。
- **现在：** 改为与任务无关的中心距离。
- **需要特定抓取位置的任务：** 由人在谓词库中补一个专门的谓词，并记为人工介入。例如，PegInsertionSide 的稠密奖励把夹爪引向插销中心往尾部 6 cm 的位置；是否需要这样的谓词，看了示范再定。

#### 3.2.4 `grasped` 的定义

- **接触力定义：** 直接用 ManiSkill 的 `is_grasping`。
  - 优点：物理上准确；与 StackCube、StackPyramid 成功判定中的“未被抓住”一致。
  - 缺点：力在图像中看不见；结果对参数敏感，PegInsertionSide 的奖励就改了 max_angle；MetaWorld、LIBERO 用 MuJoCo，接触模型不同，跨仿真器难以保持同一含义。
- **几何定义：** 在夹爪坐标系中，o 的中心落在两指垫之间的区域内，且两指间宽度与 o 在闭合方向上的厚度之差在容差内，即手指确实合在物体上，既不是张开，也不是空握。
  - 优点：§7.3 举的正是这种定义；在图像中看得见；各仿真器的算法相同。
  - 缺点：手指只是轻碰、没有夹紧时，也可能判为抓住。这种情形会让守卫提前成立，随后一抬起方块就掉落、阶段回退，正是 §3.5 的充分性检验要发现的问题。

建议：谓词库用几何定义。接触力定义保留为测量量，只用于比对：在示范和扰动 rollout 上，统计两者判定相同的帧所占的比例，并逐帧检查判定不同的地方。“比对”是单元测试的第三层（本文 §3.2.7），和 §3.5 语义检验中的“一致性”不是一回事。§7.3 的例子里还有“随夹爪抬起”，它涉及运动，建议不放进 `grasped`，而由搬运阶段守卫中的 `lifted` 来体现。

#### 3.2.6 模板（语言已定，2026-10-19）

- 每个谓词写两条模板，分别对应“需要成立”和“需要不成立”。守卫能否含取反由第 3 点定，两条先都写。
- 不变量被破坏时，另有事件模板。
- 物体名取自绑定中的显示名。
- **语言【决定，2026-10-19】：** 只保留英文模板，不另存中文版。理由是下游 VLM、VLA 和 LIBERO 的指令都是英文。例如：
  - `near(g, cube)` 需要成立："The gripper is far from the red cube; move the gripper to the red cube."
  - `grasped(g, cube)` 需要不成立："The red cube is still held; release the red cube."
  - `grasped(g, cube)` 被破坏时的事件："The red cube was dropped."

#### 3.2.7 单元测试

1. **纯张量测试（每个谓词都做）：** 构造几组位姿张量，事先确定谓词在每组位姿下应当成立还是不成立，再检查谓词算得对不对。不启动仿真，也不用示范。
2. **适配层测试（按适配层做，不按谓词做）：** 在 ManiSkill 中摆出几个构造的场景，如叠放、直立、夹住、插销尺寸各不相同。检查适配层读出的位姿、尺寸、夹爪开度、孔的位置等是否正确，以及谓词在这些场景中的结果。
3. **示范上的比对（只对有官方对应判定的谓词做）：**
   - 【事实，据官方文档（对话总结 §5.2），尚未下载核实】五个任务都有官方示范。但只有一部分谓词，在 `evaluate()` 中有对应的判定。
   - 对这部分谓词，回放示范，统计两者判定相同的比例，不要求 100%。这一层是额外的旁证，不是每个谓词都必须做。
   - 对应关系如下：
     - `grasped` ↔ `is_grasping`
     - `arm_static` ↔ PickCube 的 `is_robot_static`
     - `static` ↔ StackCube 的 `is_cubeA_static`
     - `on` ↔ `is_cubeA_on_cubeB`
     - `at` ↔ `is_obj_placed`
     - `upright ∧ on(peg, table)` ↔ LiftPegUpright 的 success
     - `inserted` ↔ PegInsertionSide 的 success
     - `next_to(A, B) ∧ on(C, A) ∧ on(C, B)`，加上静止、未被抓住 ↔ StackPyramid 的 success。它的判定比我们的组合宽，相同的比例不必是 100%。
   - 没有官方对应判定的谓词，即 `gripper_open`、`near`、`aligned`、`lifted`、`above`、`coaxial`，只做前两层。

官方示范另有一个用处：校准标为“暂定”的阈值（本文 §3.2.5）。那是建库时的调参，不属于测试。

#### 3.2.9 跨仿真器兼容（节奏已定，2026-10-19）

缘起：你担心同一个谓词在不同环境中的表示方法可能不同。

“同一个谓词”指我们自己写的那一份定义。各环境自带的判定，如 ManiSkill 的 `evaluate()` 和 LIBERO 的 BDDL 谓词，只用来判定任务是否成功，以及作为比对的参照。

差异来自三层：
- **读取状态的方式：** 字段名、坐标系、单位、桌面高度。
- **机器人和物体的几何：** 比如 Panda 与 Sawyer 的夹爪不同；物体可能是方块，也可能是碗、盘子。
- **概念本身：** 比如抽屉的“开”与门的“开”；又如 LIBERO 中“放到某个区域上”，与几何上的“放在顶面上”并不相同。

对应的五条原则：
1. **适配层输出统一的世界视图。** 单位是米，世界坐标系 z 轴向上，四元数顺序统一，每个支撑面的顶面高度由适配层给出。谓词里不写死任何环境的常数。
2. **测量量的供需要对得上。** 每个谓词声明需要的测量量，每个适配层声明能提供的测量量；某个环境提供不了，validator 就拒绝在该环境中使用这个谓词。谓词尽量只用各仿真器都能可靠给出的几何量。
3. **物体之间的差异放进对象属性。** 例如 `open(a: articulated)` 定义为：关节在“全关到全开”区间内的归一化位置 ≥ τ。抽屉和门的区别，只在于适配层给出的是哪个关节、范围是多少。
4. **同名必同义。** 含义确实不同就换名字。
5. **跨仿真器比对。** 为每个谓词准备一组标准场景，在每个仿真器里摆出同样的场景，要求判定结果相同。

节奏【决定，2026-10-19】：

- **推迟到 MetaWorld：** 第 2、3、5 条。出现第二个适配层之前，这些做了也测不出什么。
- **退路：** 适配层可以借用环境自带的判定来实现某个测量量，比如 LIBERO 的区域判定，只要它通过跨仿真器比对。

### 4.1 第 3 点：自动机的运行语义【第一版】

1. **只用线性阶段链。** 回退箭头只指向更早的阶段。
   - 计划内的 ManiSkill 任务都是固定顺序；StackPyramid 的重复抓放，把阶段依次排开即可。Φ = (k + p_k)/K 本身也要求阶段有先后。
   - LIBERO 中顺序无所谓的子任务，先指定一个顺序；策略先做了后一个时，靠第 3 条的连续前进跳过。到 LIBERO 时再看要不要分支。
2. **守卫和不变量由“文字”组成：** 一个谓词实例，或它的取反（写作 `not p(...)`）；不允许“或”。
   - 有了取反，就不必另写 `released` 一类的反义谓词；`not p` 不成立时，用 p 的“需要不成立”模板渲染。
   - 不允许“或”：guidance 说的是“还差哪些条件”，有了“或”就说不清该满足哪一个。
3. **初始阶段与连续前进：**
   - 正常重置从阶段 0 开始；从保存的状态重置时（如 LIBERO 用示范中各阶段的入口作回合起点，§6.1），阶段随状态一起给出。中途状态的阶段不能从 0 推出来，因为守卫是转换那一刻的条件，过后不一定还成立。
   - 同一步内允许连续前进：出边守卫成立就前进，直到不成立，一步最多 K 次。
4. **每一步的顺序：**
   1. 算出本步全部谓词实例的 margin 与真值，守卫、不变量、guidance 和标签都用这一份；
   2. 查当前阶段的不变量：某一条连续 m 步不成立，就回退到它声明的阶段；几条同时到期，回到其中最早的阶段；附事件；这一步不再前进；
   3. 没有回退，就按出边守卫连续前进；
   4. 按更新后的阶段计算 p_k、Φ 和 guidance。

   新进入的阶段，不变量从下一步开始检查；阶段一变，防闪烁计数清零。
5. **防闪烁放在自动机层：** 不变量连续 m 步不成立才回退，m 默认 2，作为可调参数；前进不加延迟。谓词只看当前帧，同一帧的取值唯一，交叉执行和 Stage3 的标签都需要这一点。
   - 例子：PickCube 搬运途中接触力短暂低于 0.5 N，`grasped` 闪一下假。立刻回退的话，回到 reach 后要求 `gripper_open`，而方块还在手里，阶段会卡住。
   - 回到哪个阶段由 agent 声明，回退箭头交给 Stage2 修正（本文 §3.3 第 2 项）。
6. **事件只在发生的那一步输出**（本文 §2.3 的 `event`）。文字显示多久，留到 V0、Stage3；有了逐步的事件记录，离线时按任何规则都能重算。
7. **完成状态：** 最后一个阶段的出边守卫成立后进入完成状态，Φ = 1，guidance 为空。这个守卫的各条文字成为完成状态的不变量（违反时回到最后一个阶段），最后一个阶段原有的不变量继续检查。成功信号仍取 `evaluate()["success"]`；回合因成功而终止时，终止状态的势值按 §3.3 第 2 条取 0。

### 4.2 第 4 点：阶段内 progress【第一版】

- 谓词的返回值约定为有符号的 margin：≥ 0 表示成立，单位由谓词说明。布尔读数（如 `is_grasping`）的 margin 取 +1 或 −1。margin 同时供 guidance、默认 progress 和诊断使用（本文 §2.3）。
- 每个阶段可以有一个 progress 函数，写在 `progress.py`，返回 [N]，运行时裁到 [0, 1]。progress 不参加合并，可以按名字读本任务绑定的对象，也可以调用本任务的谓词。
- 只依赖当前状态和当前阶段（本文 §2.4）。归一化只用固定尺度参数（如 reach 阶段的距离尺度 d0），在 `params` 中声明默认值和范围，供内层 BO 调。
- 没写 progress 的阶段用默认 progress：出边守卫中每条文字，成立记 1，不成立记 clip(1 + margin/scale, 0, 1)，取平均；scale 由谓词声明。这样 progress 与 guidance 指向同一组条件，agent 也可以只为个别阶段写 progress。
- 阶段交界处 Φ 不要求连续，PBRS 不要求势值连续。跳变的大小写进回放摘要，供审查和 Stage2 参考。

### 4.8 实现要点【第一版】

- **世界状态是张量快照。** 适配层每步从环境读出：
  - 绑定对象的位姿、速度、尺寸与附加属性；
  - 夹爪的 TCP 位姿、开度、手臂关节速度，以及它对每个绑定物体的 `is_grasping`；
  - 绑定物体两两之间的接触力；
  - evaluate() 的字段，放在快照的单独部分，谓词读不到，只给 validator、成功信号和里程碑用。

  谓词只读快照，不碰环境。这样，保存的状态可以离线重算，交叉执行也可以直接在别的任务的快照上运行（本文 §3.3 第 1 项）。
- **谓词**是带装饰器的函数：`@predicate(desc=..., need_true=..., need_false=..., scale=...)`，签名为 `f(w, *objects, **thresholds) -> margin[N]`；阈值是带默认值的关键字参数。
- **progress** 是函数 `progress_<阶段名>(w, o, **params) -> [N]`，`o` 是本任务绑定的对象。
- **绑定**是函数 `bind(env, api) -> {对象名: 对象说明}`：指明对应哪个 actor 或 site、尺寸，以及附加属性（可以是每步重读的函数）。
- **官方对应**写在 `stage_graph.yaml` 的 `official` 段：每条是一组文字加一个 evaluate() 的键。
- **Teacher** 先对一批状态无状态地算出全部谓词实例，再按时间更新自动机。离线处理一整条轨迹时，谓词可以一次算完全部帧。
