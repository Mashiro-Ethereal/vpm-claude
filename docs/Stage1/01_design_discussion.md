## 2. 第 1 点：产物形态与运行时接口（已定，2026-10-19）

### 2.1 产物形态【决定】

每个候选是一个目录，由一个声明式的 Stage Graph 文件和少量受限的 Python 代码组成：

- `stage_graph.yaml`：对象及其绑定（任务特有的读数在这里挂到对象上）、阶段列表、出边守卫、不变量及回退目标、guidance 的排序、谓词实例与官方字段的对应声明（本文 §3.3 第 6 项），以及全部可调参数（名称、默认值、范围）；按 schema 校验。
- `predicates.py`：该任务的测量函数和谓词，由 agent 编写，放在该任务的候选目录中，任务之间不共用（本文 §3.3 第 1 项）。原设想的 `local_predicates.py`（任务局部谓词）随共享谓词库一起取消。
- `progress.py`：各阶段的 progress 函数。

示意如下，以 PickCube 为例（本文 §3.3 第 6 项）。格式细节在第 5 点定。

```yaml
objects:          # 显示名用于模板；与仿真物体的绑定略
  g:    {name: the gripper}
  cube: {name: the red cube}
  goal: {name: the goal}
stages:
  - name: reach
    exit: [gripper_open(g), near(g, cube)]
  - name: grasp
    exit: [grasped(g, cube)]
  - name: carry
    invariants: [{pred: grasped(g, cube), regress_to: reach, event: cube_dropped}]   # 回退的语义在第 3 点定
    exit: [at_goal(cube, goal)]
  - name: settle
    invariants: [{pred: at_goal(cube, goal), regress_to: carry}]
    exit: [arm_static(g)]
official:         # 照官方判定改写的谓词实例；2026-10-21 起由第二层审查对照源码核对
  at_goal(cube, goal): is_obj_placed
params:           # 内层 BO 的搜索空间；照官方判定改写的阈值固定，不在这里
  - {name: near.g_cube.d, default: 0.02, range: [0.01, 0.05]}
```

理由：
- 【推导】内层 BO 需要显式的参数空间，外层由 LLM 改结构。用声明式文件，这两件事都变成对数据的编辑：BO 只改参数段；外层的“增删守卫谓词”“拆分阶段”可以作为离散操作记录下来，E-S1 统计错误类型时也方便。
- 【推导】schema 检查、guidance 派生、阶段等权的 Φ，都能对文件机械地完成。如果整个 teacher 是一段自由代码，这些只能靠解析代码或在运行时探测。
- 【推导】G1 比较的是“带守卫谓词的自动机”与“自由代码”，两侧都由 agent 编写，所以我们这一侧的产物本身就应当是组合式的。

“受限”的含义：
- 谓词、测量函数和 `progress.py` 只能通过适配层的世界视图读取状态，谓词还只能经参数访问物体（本文 §3.3 第 1 项的要求 2），都不能直接读仿真器内部，用 AST 检查保证。好处有三：同一份代码能离线运行在保存的状态上；换仿真器时不用改；以后落实 §7.3 的“progress 只用可观测的测量函数”也容易。
- 直接读仿真器内部的只有对象绑定这一处，由第一层的运行检查覆盖（本文 §3.3 第 2 项）。

2026-10-20 按第 2 点的结论修订：去掉类型标签；`local_predicates.py` 改为各任务的 `predicates.py`；示例改为 PickCube，并加入官方字段的对应声明。

2026-10-20 按第 3 点的结论补记：不变量不再带 `event`（本文 §4.1 第 6 条）；示例中 reach 的守卫，按分解原则只写 `near(g, cube)` 即可（本文 §4.3）；最后一个阶段的守卫加不变量对应 `success`（本文 §4.1 第 7 条）。2026-10-21 补记：参数名按谓词，如 `near.max_dist`，示例中按实例的 `near.g_cube.d` 作废（本文 §4.2）。示例本身不再改写。

备选（未采用）：整个候选写成受限的 Python DSL。它的好处是 G1 的两侧都是 Python，比较时不混入文件格式的差别。采用声明式文件后，两侧的文件格式不同（YAML 加代码，对比纯代码），这一点在第 8 点讨论 G1 的对照设计时处理。

### 2.2 运行时【决定】

- 测量函数、谓词、progress 和自动机更新，都写成对 `[N]` 批量张量的 torch 运算，与仿真放在同一设备上，不允许逐环境循环，也不用 `.item()`。示范、Stage2 保存的状态和 Stage3 重标都走同一份代码，离线处理时 N 就是帧数。
  - 【事实】ManiSkill 官方 PPO 配置用 2048–4096 个 GPU 并行环境（[对话总结](../00_conversation_digest.md) §5.2）。
  - 【假设】teacher 如果逐个环境用 Python 计算，会成为训练瓶颈；开销需要实测。
- 代码分三层：
  1. **适配层**（每个仿真器一个，由人写）：从特权状态读出通用物理量，如物体位姿与尺寸、速度、TCP 位姿、夹爪开度、两两接触力；通用函数算出的判定（如 Panda 的 `is_grasping(obj)`、`is_static`）也作为读数提供。`evaluate()` 字段另行提供，只给 validator 和成功信号用（本文 §3.3 第 6 项）。
  2. **测量函数、谓词与 progress**（每个任务由 agent 写，与仿真器无关）：只通过适配层的世界视图取数。
  3. **自动机运行时**（与仿真器无关，由人写）：读 Stage Graph 文件，跟踪阶段，计算 Φ 和 guidance。
- 【推导】扩展到 MetaWorld、LIBERO 时，只需新写适配层。跨任务的一致性由事后归纳的共享词表处理；跨仿真器合并，要求各适配层的世界视图单位和坐标系一致（本文 §3.3 第 1 项）。
- 2026-10-20 按第 2 点的结论修订：原第 2 层是共享的谓词库，现为各任务自己的谓词。

### 2.3 每一步的输出【决定】

| 字段 | 形状 | 含义 |
| --- | --- | --- |
| `stage` | `[N]` 整数 | 当前阶段 k |
| `stage_progress` | `[N]` | p_k ∈ [0, 1] |
| `phi` | `[N]` | (k + p_k) / K |
| `pred` | `[N, P]` 布尔 | 文件中用到的谓词实例（守卫、不变量、里程碑）的取值 |
| `margin` | `[N, P]` | 有符号的“离阈值还差多少”，例如 `near` 取 d_max − d；供分级谓词、progress 和诊断使用 |
| `guidance` | `[N, P]` 布尔 | 当前阶段出边守卫中不成立的谓词 |
| `event` | `[N]` 整数 | 本步是否有不变量被破坏，回退到哪个阶段 |
| `milestone` | `[N, M]` 布尔 | 固定里程碑的取值，供 Stage2 早期评价（第 8 点） |

- 2026-10-20 补记：`event` 一栏取消（本文 §4.1 第 6 条），回退可从 `stage` 序列离线算出。2026-10-21 补记：`milestone` 一栏也取消，里程碑改由适配层用通用读数计算，放在 Stage2（本文 §4.6）。
- 成功信号不由 teacher 给出，取环境的 `evaluate()["success"]`（§3.3 第 3 条）。
- 训练循环里不渲染文字；需要文字时，再由 `guidance` 加模板生成。
- §5.3 要求视觉 VPM 预测“每个合法谓词实例”。Stage1、Stage2 只算文件中用到的实例，全部合法实例等 Stage3 重标时再枚举，以节省训练时的计算。

### 2.4 状态依赖【决定】

- 谓词和 progress 只依赖当前时刻的完整物理状态，位姿和速度都算当前状态。不记录“进入阶段时的初始距离”这类快照；归一化用固定尺度参数，交给内层 BO 调（细节在第 4 点）。
- teacher 中依赖历史的只有自动机的当前阶段，这是 §3.2 有意保留的“最小记忆”。所以 `Φ = (k + p_k(s)) / K` 只通过 k 依赖历史。
- 每个环境记一个当前阶段（以及第 3 点要定的防闪烁计数），环境重置时按 `env_idx` 重置。
- 理由：
  - 【事实，据 [PRM4RL 精读笔记](../../references/notes/base_progress_reward.md)“限制”第 2 条，没有重读原文】PRM4RL 附录 A.6 的公开示例中，进度错误出在两处：归一化的基准距离取错，使接近阶段的进度恒为 0；到达目标时势值反而下降。
  - 【推导】快照会让同一帧的标签依赖历史：视觉 VPM 学不到，也会干扰“阶段是否只由当前状态决定”这项检查。

#### 3.2.2 类型标签与适配层

- **类型标签（可多重）：** 共六个：
  - `end_effector`；
  - `graspable`；
  - `support`：桌面，以及可以在上面放东西的方块；
  - `region`：无碰撞的目标区域；
  - `axial`：有主轴的物体，如插销；
  - `receptacle`：带孔、可供插入的物体，如 PegInsertionSide 的盒子。

  例如，StackCube 的绿块同时是 `graspable` 和 `support`。
- **适配层提供的量：**
  - 每个绑定的对象：位姿、线速度与角速度、半尺寸 `[N, 3]`，以及按类型需要的属性：`axial` 的主轴和头部位置，`receptacle` 的孔位姿与孔半径，`region` 的区域半径；
  - 夹爪：TCP 位姿、两指间宽度、指垫位姿、手臂关节速度；两指与物体的接触力只在用到时才算；
  - 桌面：作为一个 `support` 对象，顶面 z = 0。
- **几何量：** 最低点、顶面高度等，都由位姿和半尺寸按有向包围盒计算，物体倾斜时也成立。
- **与 §3.7 的差别：**
  - §3.7 的例子中，“支撑面或目标区域”是一个标签。这里拆成 `support` 和 `region`，因为 PickCube 的目标是空中的一个点，没有顶面，`on` 无法定义。
  - 另外新增 `axial`（供 `upright`、`coaxial`、`inserted` 使用）和 `receptacle`（供 `coaxial`、`inserted` 使用）。
  - 这两处都是对 §3.7 示例的细化，不改动设计。
- **v1 的范围：** 只考虑 Panda 和自上而下的抓取。
  - 【事实，据源码】五个任务的默认机器人都是 Panda。其中 StackCube、PegInsertionSide、StackPyramid 默认用 panda_wristcam，机械臂和夹爪相同，只多一个腕部相机。
  - 适配层的夹爪几何按 Panda 写；`aligned` 只比较水平面内的朝向。
  - LiftPegUpright 的抓法是否属于自上而下，要看了示范再确认。

`near` 的定义在 2026-10-19 作了修改：

- **需要特定抓取位置的任务：** 由人在谓词库中补一个专门的谓词，并记为人工介入。例如，PegInsertionSide 的稠密奖励把夹爪引向插销中心往尾部 6 cm 的位置；是否需要这样的谓词，看了示范再定。

#### 3.2.4 `grasped` 的定义

- **接触力定义：** 直接用 ManiSkill 的 `is_grasping`。
  - 优点：物理上准确；与 StackCube、StackPyramid 成功判定中的“未被抓住”一致。
  - 缺点：力在图像中看不见；结果对参数敏感，PegInsertionSide 的奖励就改了 max_angle；MetaWorld、LIBERO 用 MuJoCo，接触模型不同，跨仿真器难以保持同一含义。
- **几何定义：** 在夹爪坐标系中，o 的中心落在两指垫之间的区域内，且两指间宽度与 o 在闭合方向上的厚度之差在容差内，即手指确实合在物体上，既不是张开，也不是空握。
  - 优点：§7.3 举的正是这种定义；在图像中看得见；各仿真器的算法相同。
  - 缺点：手指只是轻碰、没有夹紧时，也可能判为抓住。这种情形会让守卫提前成立，随后一抬起方块就掉落、阶段回退，正是 §3.5 的充分性检验要发现的问题。

建议：谓词库用几何定义。接触力定义保留为测量量，只用于比对：在示范和扰动 rollout 上，统计两者判定相同的帧所占的比例，并逐帧检查判定不同的地方。“比对”是单元测试的第三层（本文 §3.2.7），和 §3.5 语义检验中的“一致性”不是一回事。§7.3 的例子里还有“随夹爪抬起”，它涉及运动，建议不放进 `grasped`，而由搬运阶段守卫中的 `lifted` 来体现。

#### 3.2.5 阈值

#### 3.2.7 单元测试

1. **纯张量测试（每个谓词都做）：** 构造几组位姿张量，事先确定谓词在每组位姿下应当成立还是不成立，再检查谓词算得对不对。不启动仿真，也不用示范。
2. **适配层测试（按适配层做，不按谓词做）：** 在 ManiSkill 中摆出几个构造的场景，如叠放、直立、夹住、插销尺寸各不相同。检查适配层读出的位姿、尺寸、夹爪开度、孔的位置等是否正确，以及谓词在这些场景中的结果。
3. **示范上的比对（只对有官方对应判定的谓词做）：**
   - 【事实，据官方文档（对话总结 §5.2），尚未下载核实】五个任务都有官方示范。但只有一部分谓词，在 `evaluate()` 中有对应的判定。
   - 对这部分谓词，回放示范，统计两者判定相同的比例，不要求 100%。这一层是额外的旁证，不是每个谓词都必须做。
   - 对应关系如下：
     - `grasped` ↔ `is_grasping`
     - `arm_static` ↔ PickCube 的 `is_robot_static`
     - `static` ↔ StackCube 的 `is_cubeA_static`

#### 3.2.9 跨仿真器兼容（节奏已定，2026-10-19）

缘起：你担心同一个谓词在不同环境中的表示方法可能不同。

“同一个谓词”指我们自己写的那一份定义。各环境自带的判定，如 ManiSkill 的 `evaluate()` 和 LIBERO 的 BDDL 谓词，只用来判定任务是否成功，以及作为比对的参照。

差异来自三层：
- **读取状态的方式：** 字段名、坐标系、单位、桌面高度。
- **机器人和物体的几何：** 比如 Panda 与 Sawyer 的夹爪不同；物体可能是方块，也可能是碗、盘子。
- **概念本身：** 比如抽屉的“开”与门的“开”；又如 LIBERO 中“放到某个区域上”，与几何上的“放在顶面上”并不相同。

对应的五条原则：
1. **适配层输出统一的世界视图。** 单位是米，世界坐标系 z 轴向上，四元数顺序统一，每个支撑面的顶面高度由适配层给出。谓词里不写死任何环境的常数。
2. **测量量的供需要对得上。** 每个谓词声明需要的测量量，每个适配层声明能提供的测量量；某个环境提供不了，validator 就拒绝在该环境中使用这个谓词。谓词尽量只用各仿真器都能可靠给出的几何量。
3. **物体之间的差异放进对象属性。** 例如 `open(a: articulated)` 定义为：关节在“全关到全开”区间内的归一化位置 ≥ τ。抽屉和门的区别，只在于适配层给出的是哪个关节、范围是多少。
4. **同名必同义。** 含义确实不同就换名字。
5. **跨仿真器比对。** 为每个谓词准备一组标准场景，在每个仿真器里摆出同样的场景，要求判定结果相同。

节奏【决定，2026-10-19】：
- **现在（ManiSkill 阶段）：** 只守第 1 条和第 4 条，几乎不额外花工夫。第 1 条中“谓词只通过适配层取数”已在第 1 点定下。
- **推迟到 MetaWorld：** 第 2、3、5 条。出现第二个适配层之前，这些做了也测不出什么。
- **退路：** 适配层可以借用环境自带的判定来实现某个测量量，比如 LIBERO 的区域判定，只要它通过跨仿真器比对。
- **检查点：** MetaWorld 第一层任务做完时，统计谓词库中的谓词有多少保持了原来的含义、有多少需要拆分。如果拆分太多，就把主张收窄为“各仿真器内部复用”，这对 Stage2 和 V0 已经够用。
- **仍可能不够的地方：** LIBERO 的碗、盘子、篮子等非方块物体，用有向包围盒判定 `on`、`inside` 可能太粗。LIBERO 中 BDDL 谓词的具体判定方式尚未核对，扩展到 LIBERO 时再看。

### 4.8 实现要点【决定，2026-10-21，随第 9 点确认】

- **世界状态是张量快照。** 适配层每步从环境读出：
  - 绑定对象的位姿、速度、尺寸与附加属性；

- **绑定**是函数 `bind(env, api) -> {对象名: 对象说明}`：指明对应哪个 actor 或 site、尺寸，以及附加属性（可以是每步重读的函数）。

2. **夹爪的接触力是两个手指受力大小之和。** 原写法是“the sum over its two fingers”，没说是先求和再取大小，还是先取大小再求和；现写明后者，与 `is_grasping` 分别看两个手指的做法一致。
3. **附加属性怎么区分“每个环境一个值”与“所有环境共用”：** 首维为 N（或 1）的值按环境区分，其余的值所有环境共用；长度恰好等于 N 的共用向量要写成 `[1, ...]`。这是张量广播的通常约定，写进 candidate_api.md 免得 agent 踩到。

另有一处只在内部、agent 看不到：快照中 `evaluate()` 的字段一律转成 float32（成功信号为 0 或 1），记在 02。
