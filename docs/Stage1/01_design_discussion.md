### 1.2 对 Stage1 的理解（2026-10-19 复述，你未提出异议）

- **定位：** Stage1 把一个任务的过程知识自动写成程序，即过程 teacher 的初始候选。程序读仿真特权状态，可以逐步执行。
  - 语义是否正确、进度是否好用，由 Stage2 用特权状态策略的训练反馈来检验和修正。
  - Stage1 要保证三点：派生产物一致；能在实际环境中运行；结构和参数可以分开修改，方便 Stage2 的两层搜索（§3.1、§3.6、§4.2）。
- **表示：** 过程 teacher 由 Stage Graph 和阶段内 progress 组成。
  - Stage Graph 是带守卫谓词的阶段自动机：节点是阶段；前向边上的守卫是谓词的合取；每个阶段标明需要保持的不变量，不变量被破坏时，沿回退箭头回到能重新建立它的阶段。
  - 谓词取自带类型签名的共享谓词库，分为测量函数、基本谓词、派生谓词三层。
  - 三种输出出自同一结构：阶段；势值 `Φ = (k + p_k(s; θ_k)) / K`；guidance，即当前阶段出边守卫中不成立的谓词，用模板渲染，不变量被破坏时另附一条事件说明（§3.2–§3.4、§3.7）。
- **分工：**
  - 人：定义类型体系和核心谓词，并配单元测试。
  - LLM（DeepSeek，Harness 用 Claude Code）：对每个任务标注对象类型、划分阶段、组合守卫、标出不变量与回退、编写 progress。
  - 新谓词：先作为任务局部谓词，附类型签名和测试状态；被多个任务用到后，经人工审核才升入共享库（§3.7、§9 第 1 项）。
- **检验：**
  - ArtifactValidator 检查结构、派生产物一致性和类型签名；EnvGroundedValidator 检查代码能否在真实环境接口上运行。两者报告的问题驱动有界修复。
  - 五项语义检验：必要性与充分性、可执行性、预测性、一致性、阶段是否只由当前状态决定。其中需要“保存的 rollout”的几项，Stage1 只能先用示范或构造的数据做一部分，完整版要等 Stage2（§3.5、§6.4）。
- **范围与实验：**
  - 任务：ManiSkill 的 PickCube、LiftPegUpright（第一层），以及 StackCube、PegInsertionSide、StackPyramid（第二层）。
  - 实验：G1 和谓词库增长曲线（§6.1、§6.2）。
  - 下游对 teacher 的三项硬要求：
    - 作为奖励时，满足 §3.3 的六条规则；
    - 能在 GPU 上对全部并行环境批量计算（由 §6.3 的 GPU 并行 PPO 推出）；
    - 能在保存的状态上重放，供 Stage3 重标（§5.2）。

## 2. 第 1 点：产物形态与运行时接口（已定，2026-10-19）

### 2.1 产物形态【决定】

每个候选是一个目录，由一个声明式的 Stage Graph 文件和少量受限的 Python 代码组成：

- `stage_graph.yaml`：对象及其类型标签与绑定、阶段列表、出边守卫、不变量及回退目标、guidance 的排序，以及全部可调参数（名称、默认值、范围）；按 schema 校验。
- `progress.py`：各阶段的 progress 函数。
- `local_predicates.py`（可选）：任务局部谓词。

示意如下。格式细节在第 5 点定，类型标签和谓词以第 2 点的结论为准。

```yaml
objects:
  g:      {tags: [end_effector]}
  cube:   {tags: [graspable]}
  target: {tags: [support]}
stages:
  - name: approach
    exit: [gripper_open(g), near(g, cube), aligned(g, cube)]
  - name: grasp
    exit: [grasped(g, cube)]
  - name: transport
    invariants: [{pred: grasped(g, cube), regress_to: approach, event: cube_dropped}]
    exit: [lifted(cube), above(cube, target)]
  - name: place
    exit: [on(cube, target), gripper_open(g)]
params:   # 内层 BO 的搜索空间
  - {name: near.g_cube.d_max, default: 0.02, range: [0.01, 0.05]}
```

理由：
- 【推导】内层 BO 需要显式的参数空间，外层由 LLM 改结构。用声明式文件，这两件事都变成对数据的编辑：BO 只改参数段；外层的“增删守卫谓词”“拆分阶段”可以作为离散操作记录下来，E-S1 统计错误类型时也方便。
- 【推导】类型检查、guidance 派生、阶段等权的 Φ，都能对文件机械地完成。如果整个 teacher 是一段自由代码，这些只能靠解析代码或在运行时探测。
- 【推导】G1 比较的正是“谓词库组合”与“自由代码”，所以我们这一侧的产物本身就应当是组合式的。

“受限”的含义：
- `progress.py` 和任务局部谓词只能通过测量函数读取状态，不能直接读仿真器内部，用 AST 检查保证。好处有三：同一份代码能离线运行在保存的状态上；换仿真器时不用改；以后落实 §7.3 的“progress 只用可观测的测量函数”也容易。
- 直接读仿真器内部的只有对象绑定这一处，由 EnvGroundedValidator 检查。

备选（未采用）：整个候选写成受限的 Python DSL。它的好处是 G1 的两侧都是 Python，比较时不混入文件格式的差别。采用声明式文件后，两侧的文件格式不同（YAML 加代码，对比纯代码），这一点在第 8 点讨论 G1 的对照设计时处理。

### 2.2 运行时【决定】

- 测量函数、谓词、progress 和自动机更新，都写成对 `[N]` 批量张量的 torch 运算，与仿真放在同一设备上，不允许逐环境循环，也不用 `.item()`。示范、Stage2 保存的状态和 Stage3 重标都走同一份代码，离线处理时 N 就是帧数。
  - 【事实】ManiSkill 官方 PPO 配置用 2048–4096 个 GPU 并行环境（[对话总结](../00_conversation_digest.md) §5.2）。
  - 【假设】teacher 如果逐个环境用 Python 计算，会成为训练瓶颈；开销需要实测。
- 代码分三层：
  1. **适配层**（ManiSkill 专用）：从特权状态读出通用物理量，如物体位姿与尺寸、速度、TCP 位姿、夹爪开度、两两接触力。
  2. **谓词库**（与仿真器无关）：只通过适配层取数。
  3. **自动机运行时**（与仿真器无关）：读 Stage Graph 文件，跟踪阶段，计算 Φ 和 guidance。
- 【推导】扩展到 MetaWorld、LIBERO 时，只需新写适配层。各仿真器用同一份谓词代码，跨任务共享的谓词含义才有保障。

### 2.3 每一步的输出【决定】

| 字段 | 形状 | 含义 |
| --- | --- | --- |
| `stage` | `[N]` 整数 | 当前阶段 k |
| `stage_progress` | `[N]` | p_k ∈ [0, 1] |
| `phi` | `[N]` | (k + p_k) / K |
| `pred` | `[N, P]` 布尔 | 文件中用到的谓词实例（守卫、不变量、里程碑）的取值 |
| `margin` | `[N, P]` | 有符号的“离阈值还差多少”，例如 `near` 取 d_max − d；供分级谓词、progress 和诊断使用 |
| `guidance` | `[N, P]` 布尔 | 当前阶段出边守卫中不成立的谓词 |
| `event` | `[N]` 整数 | 本步是否有不变量被破坏，回退到哪个阶段 |
| `milestone` | `[N, M]` 布尔 | 固定里程碑的取值，供 Stage2 早期评价（第 8 点） |

- 成功信号不由 teacher 给出，取环境的 `evaluate()["success"]`（§3.3 第 3 条）。
- 训练循环里不渲染文字；需要文字时，再由 `guidance` 加模板生成。
- §5.3 要求视觉 VPM 预测“每个合法谓词实例”。Stage1、Stage2 只算文件中用到的实例，全部合法实例等 Stage3 重标时再枚举，以节省训练时的计算。

### 2.4 状态依赖【决定】

- 谓词和 progress 只依赖当前时刻的完整物理状态，位姿和速度都算当前状态。不记录“进入阶段时的初始距离”这类快照；归一化用固定尺度参数，交给内层 BO 调（细节在第 4 点）。
- teacher 中依赖历史的只有自动机的当前阶段，这是 §3.2 有意保留的“最小记忆”。所以 `Φ = (k + p_k(s)) / K` 只通过 k 依赖历史。
- 每个环境记一个当前阶段（以及第 3 点要定的防闪烁计数），环境重置时按 `env_idx` 重置。
- 理由：
  - 【事实，据 [PRM4RL 精读笔记](../../references/notes/base_progress_reward.md)“限制”第 2 条，没有重读原文】PRM4RL 附录 A.6 的公开示例中，进度错误出在两处：归一化的基准距离取错，使接近阶段的进度恒为 0；到达目标时势值反而下降。
  - 【推导】快照会让同一帧的标签依赖历史：视觉 VPM 学不到，也会干扰“阶段是否只由当前状态决定”这项检查。

### 2.5 交付物与生成次数【决定】

- **基础设施（做一次）：** 适配层、谓词库及单元测试、自动机运行时、两层 validator 与语义检验、生成 harness。
- **每个任务：** 通过 validator 的初始候选，附生成记录和检验报告。
- **生成次数：** “K 次独立生成”就是把同一个生成流程独立跑 K 次，每次从头开始，只有采样的随机性不同。
  - 先把一次生成写好，K 留到第 8 点（G1）再定。
  - 实现上要求每次运行有独立的目录和完整记录，以后重复多次时不用改代码。
- 【推导】K > 1 以后有两个用处：
  - G1 需要错误率的分布，而 PRM4RL 没有报告生成可靠性（精读笔记“限制”第 3 条）；
  - Stage2 需要初始候选。

## 3. 第 2 点：谓词库 v1 与 ManiSkill 适配层（已提出建议，待讨论）

### 3.1 核对到的 ManiSkill 事实【事实】

**阅读范围：** 2026-10-19 阅读了 GitHub 上 ManiSkill v3.0.1 标签的以下源码：
- 五个任务文件的全文；
- Panda 的 `is_grasping` 与 `is_static`；
- Actor 的几何与速度接口。

阅读方式是用 curl 把源码输出到终端，没有存盘，也没有运行。仓库已从 haosulab/ManiSkill 迁到 mani-skill/ManiSkill；PyPI 上的最新版本是 3.0.1（2026-04-21 发布）。

| 任务 | 回合上限 | 成功条件（`evaluate()`） | 与设计有关的细节 |
| --- | --- | --- | --- |
| PickCube-v1 | 50 | 方块中心到目标点 ≤ 0.025 m，且手臂静止（关节速度绝对值的最大值 ≤ 0.2） | 目标是空中的点（高 0.02–0.32 m），用无碰撞的球表示；成功不要求松手 |
| LiftPegUpright-v1 | 50 | XYZ 欧拉角的 \|euler_z\| 与 π/2 相差 < 0.08，且中心高度与半长 0.12 相差 < 0.005 | 即竖立在桌面上；文档写“y euler angle”，代码用的是 `euler[:, 2]` |
| StackCube-v1 | 50 | 红块在绿块上（xy 偏移 ≤ 0.033 m，高差与 0.04 相差 ≤ 0.005），红块静止，且未被抓住 | 默认机器人是 panda_wristcam |
| PegInsertionSide-v1 | 100 | 插销头（+x 端，橙色）在孔坐标系中 x ≥ −0.015，y、z 在孔半径内 | 每个并行环境的插销和盒子尺寸不同，合并成一个 Actor；文档的成功条件写“白色一端” |
| StackPyramid-v1 | 250 | A、B 相邻（只看 xy ≤ 0.062 m）；C 在 A、B 之上（xy ≤ 0.062 m 且 \|dz\| > 0.02，不看正负）；A、C 静止，且未被抓住 | 奖励模式只有 none 和 sparse |

另有三点：
- Panda 的 `is_grasping(obj, min_force=0.5, max_angle=85)` 要求两指与物体的接触力都 ≥ 0.5 N，且力的方向与手指张开方向的夹角 ≤ 85°。PegInsertionSide 自己的稠密奖励改用了 max_angle=20。
- `Actor.get_collision_meshes()` 在 CPU 上计算，没有缓存，也不支持合并后的 Actor，所以取不到 PegInsertionSide 插销和盒子的碰撞网格。
- 桌面高度 z = 0。

对设计的影响：
1. 【推导】`evaluate()` 是成功判定，不是谓词库。StackPyramid 的“相邻”把叠在一起也算进去，“在上面”不分上下。我们的谓词要有自己的语义；与 `evaluate()` 字段比对只作为合理性检查，不当作真值。
2. 【事实】文档与代码又多了一处不一致（LiftPegUpright），此前已知 PegInsertionSide 有一处（对话总结 §5.2）。PickCube 不要求松手，LiftPegUpright 要求立在桌上，这两点也都和 §3.2 抓放例子的模式不同。这些都支持第 5 点给 LLM 源码，而不只给文档。
3. 【推导】物体尺寸要按环境取成 `[N, 3]` 张量，从环境属性（如 `peg_half_sizes`）绑定，不能依赖碰撞网格。

### 3.2 建议【待定】

#### 3.2.1 核心库按哪些任务定

§6.2 的增长曲线要求用第一层和一部分第二层任务开发核心库，其余任务逐个加入，记录每个任务新增的谓词。如果现在按五个任务一起设计核心库，ManiSkill 上的增长曲线从构造上就恒为零，失去意义。

建议：
- **开发集：** PickCube、LiftPegUpright、StackCube。
- **留出：** PegInsertionSide、StackPyramid。它们需要的新谓词（预计是 `coaxial`、`inserted`、`next_to`）由 LLM 作为任务局部谓词提出，计入增长曲线，也正好提前检验任务局部谓词的流程。
- **暂缓：**
  - §6.2 示例列表中的 `inserted` 因此暂不进核心库；开发集用不到的 `not_dropped` 也暂缓。
  - `open`、`closed`、`pressed`、`inside` 等，到 MetaWorld、LIBERO 的开发集任务时再加；LIBERO 的完成谓词按 §6.2 作为外部种子。

#### 3.2.2 类型标签与适配层

- **类型标签（可多重）：** 共五个：
  - `end_effector`；
  - `graspable`；
  - `support`：桌面，以及可以在上面放东西的方块；
  - `region`：无碰撞的目标区域；
  - `axial`：有主轴的物体，如插销。

  例如，StackCube 的绿块同时是 `graspable` 和 `support`。
- **适配层提供的量：**
  - 每个绑定的对象：位姿、线速度与角速度、半尺寸 `[N, 3]`，以及可选的主轴、抓取点偏移和区域半径；
  - 夹爪：TCP 位姿、两指间宽度、指垫位姿、手臂关节速度；两指与物体的接触力只在用到时才算；
  - 桌面：作为一个 `support` 对象，顶面 z = 0。
- **几何量：** 最低点、顶面高度等，都由位姿和半尺寸按有向包围盒计算，物体倾斜时也成立。

#### 3.2.3 核心谓词 v1（开发集）

| 谓词 | 签名 | 定义 | 默认阈值（来源） |
| --- | --- | --- | --- |
| `gripper_open(g)` | g: end_effector | 两指间宽度 ≥ w | 0.07 m（全开约 0.08 m） |
| `near(g, o)` | g: end_effector, o: graspable | TCP 到 o 的抓取点的距离 ≤ d；抓取点默认取中心，可在绑定中给偏移 | 0.02 m（暂定） |
| `aligned(g, o)` | 同上 | 夹爪闭合方向与 o 的抓取方向在水平面内的夹角 ≤ θ，按 o 的对称性取模（方块 90°，长条 180°） | 10°（暂定） |
| `grasped(g, o)` | 同上 | 见本文 §3.2.4 | — |
| `arm_static(g)` | g: end_effector | 手臂关节速度绝对值的最大值 ≤ v | 0.2（PickCube） |
| `lifted(o)` | o: graspable | o 的最低点高出桌面 ≥ h | 0.02 m（暂定） |
| `above(o, t)` | o: graspable, t: support | o 的中心投影落在 t 的顶面内（含余量 m），且 o 的最低点高于 t 的顶面 | m = 0.005 m |
| `on(o, t)` | o: graspable, t: support | 投影条件同上，且 o 的最低点与 t 的顶面高差 ≤ ε | m = ε = 0.005 m（参照 StackCube） |
| `at(o, r)` | o: graspable, r: region | o 的中心到区域中心的距离 ≤ 区域半径 | 0.025 m（PickCube） |
| `static(o)` | o: graspable | 线速度 ≤ v，且角速度 ≤ ω | 0.01、0.5（StackCube） |
| `upright(o)` | o: graspable + axial | 主轴与竖直方向的夹角 ≤ θ | 0.08 rad（参照 LiftPegUpright） |

派生谓词只有 `placed(o, t) = on(o, t) ∧ ¬grasped(g, o)`（§3.7 的例子）。

#### 3.2.4 `grasped` 的定义

- **接触力定义：** 直接用 ManiSkill 的 `is_grasping`。
  - 优点：物理上准确；与 StackCube、StackPyramid 成功判定中的“未被抓住”一致。
  - 缺点：力在图像中看不见；结果对参数敏感，PegInsertionSide 的奖励就改了 max_angle；MetaWorld、LIBERO 用 MuJoCo，接触模型不同，跨仿真器难以保持同一含义。
- **几何定义：** 在夹爪坐标系中，o 的中心落在两指垫之间的区域内，且两指间宽度与 o 在闭合方向上的厚度之差在容差内，即手指确实合在物体上，既不是张开，也不是空握。
  - 优点：§7.3 举的正是这种定义；在图像中看得见；各仿真器的算法相同。
  - 缺点：手指只是轻碰、没有夹紧时，也可能判为抓住。

建议：核心库用几何定义。接触力定义保留为测量量，只用于一致性检验：在示范和扰动 rollout 上报告两者的一致率，并检查不一致的帧。§7.3 的例子里还有“随夹爪抬起”，它涉及运动，建议不放进 `grasped`，而由搬运阶段守卫中的 `lifted` 来体现。

#### 3.2.5 阈值

- 标为“暂定”的阈值，开发时用官方示范校准：看示范在关键时刻（如夹爪刚合上时）的测量值分布，让守卫在示范上能被满足。
- 每个阈值都附可调范围，供内层 BO 使用。
- 按 §9 第 5 项的过渡安排，任务可以按实例覆盖库默认值。

#### 3.2.6 模板

- 每个谓词写两条模板，分别对应“需要成立”和“需要不成立”。守卫能否含取反由第 3 点定，两条先都写。
- 不变量被破坏时，另有事件模板。
- 物体名取自绑定中的显示名。
- 建议以英文为准，因为下游 VLM、VLA 和 LIBERO 的指令都是英文；中文只用于展示。例如：
  - `near(g, cube)` 需要成立："The gripper is far from the red cube; move the gripper to the red cube."
  - `grasped(g, cube)` 需要不成立："The red cube is still held; release the red cube."
  - `grasped(g, cube)` 被破坏时的事件："The red cube was dropped."

#### 3.2.7 单元测试

1. **纯张量测试：** 构造位姿张量，检查测量函数和谓词，不启动仿真。
2. **仿真测试：** 在 ManiSkill 中摆出构造的场景后计算谓词，包括叠放、直立，以及插销尺寸各不相同的情况。
3. **示范一致性：** 回放官方示范，把谓词与 `evaluate()` 的对应字段比对，报告一致率，不要求 100%。对应关系为：
   - `grasped` ↔ `is_grasping`
   - `on` ↔ `is_cubeA_on_cubeB`
   - `at` ↔ `is_obj_placed`
   - `upright ∧ on(peg, table)` ↔ LiftPegUpright 的 success

#### 3.2.8 任务局部谓词的测试状态

- 由 LLM 给出场景配置：物体位姿（可以相对其他物体或 TCP 给出）和两指宽度。
- 构造时把物体摆到夹爪旁边，而不移动机械臂，这样可以避开逆运动学。
- 纯几何的谓词摆好就能算；涉及速度或接触的，先仿真几步再算。
- 具体格式在第 5 点定。
